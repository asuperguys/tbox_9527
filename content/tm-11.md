## 二、背景与痛点(为什么要改)

原实现(`external_data_process.cpp`)的问题:

| # | 问题 | 高频场景(1700帧/s)下的放大效应 |
|---|------|--------------------------------|
| 1 | **整体覆盖**:每次收包新建 `DashboardData_t` 整体赋值 | 不同 ID 帧交错到达,未在本帧出现的字段被**误清为默认值** → 数据错乱 |
| 2 | **无超时**:车速/刹车等状态型数据停止更新后仍被当有效 | 业务(算法/三急/倒车)拿**陈旧数据**做判定 → 误报 |
| 3 | **业务阻塞收包**:三急判定直接在收包线程同步执行 | 高频下收包线程被拖死 → 丢帧 |
| 4 | **高频日志**:六轴每帧 LogInfo | 日志风暴 → IO 打满,系统卡顿 |
| 5 | **无变化检测** | 消费端无法判断"是否有新数据",相同数据重复计算 |
| 6 | **无批量** | 每帧多次独立操作,锁开销累积 |

## 三、方案设计(信号级处理,AUTOSAR COM 思想)

### 3.1 核心思路

```
收包线程(生产者)                        业务线程(消费者)
CAN报文/数据项 ──拆解为独立信号──▶ CanSignalMgr ──按需读取──▶ 算法/三急/倒车
                                  (注册表+信号槽)   带有效性判断
```

**解耦本质**:解析只负责"把报文变成信号"并写入槽;业务只负责"读信号并判断是否可用"。两者通过信号槽间接联系,互不阻塞。

### 3.2 六大设计要素

| 要素 | 实现 | 解决 |
|------|------|------|
| 信号注册表 | `CanSignalDesc_t` 一行注册(ID/类型/超时/缩放/回调) | 新增信号零侵入,配置驱动 |
| 信号槽 | 预分配 `CanSignalSlot_t[64]`,sigId 紧凑时 O(1) 索引 | 零动态内存,快速查找 |
| 批量更新 | `updateBatch` 单锁一次处理多信号 | 减少锁开销(1700帧/s 友好) |
| 超时监控 | 500ms 超时:读时惰性判断 + 1s 周期线程主动检查 | 状态型信号失效自动置无效 |
| 变化检测 | 每信号 `version` 计数 | 消费端判断"有新数据才处理" |
| 降频处理 | 三急 100ms 节流、日志 5s 节流 | 业务不在收包路径上每帧跑 |

### 3.3 为什么这样设计(面试必答:取舍)

1. **为什么用"信号"而不是"结构体"?**
   > CAN 报文是帧/数据项流,不同 ID 帧更新不同字段。用结构体整体存储,必须等"所有字段齐了"才可用,且无法表达"某个字段单独过期"。信号是更细的粒度——每个字段独立存储、独立超时、独立更新,天然匹配 CAN 语义。
2. **为什么超时用"惰性判断 + 周期检查"双保险?**
   > 惰性判断(getWithTime 读时比较时间戳)保证"消费者永远拿不到陈旧数据",即使没人调周期检查;周期线程(checkTimeout)负责主动置无效并触发回调,用于日志/联动。一个保正确性,一个保及时性。
3. **为什么 signalId 要求紧凑?**
   > 紧凑 ID 直接数组索引 O(1),不用哈希表——嵌入式高频场景避免哈希碰撞和内存开销。用空间换时间。
4. **为什么单锁批量?**
   > 1700帧/s 时加锁本身是开销。一次收包往往含多个数据项(如六轴 6 个轴),攒成一个批次单锁更新,锁竞争降到 1/6。
5. **为什么框架零依赖?**
   > 时间戳由调用方传入(不内部取系统时间),日志回调由注册方提供——框架只做"信号管理"一件事,任何平台可移植。这体现了**单一职责**。

```cpp
int ExternalDataProcess::DashboardDataParse(char *data, int packetLen)

    ...
```

### 4.5 超时监控可选化(方案B落地,2026-08 优化)

> 按 [14 文档](#/tm-14)复盘结论落地:超时线程从"SignalInit 内自启"改为**独立可选接口**。

```cpp
// 1) SignalInit:只注册信号,不启线程
ExternalDataProcess::instance()->SignalInit();

// 2) StartTimeoutMonitor:按需启动1s周期主动超时检查线程(可选)
ExternalDataProcess::instance()->StartTimeoutMonitor();
//    不调用也没问题:读取时惰性判断(getWithTime)已保证"拿不到陈旧数据",
//    主动线程仅用于"及时置无效+触发回调"。
```

**取舍**:惰性判断 = 保正确性(必须);主动线程 = 保及时性(可选)。
数据率低、无需回调的产品可省略线程,减少常驻资源——这正回应了"是不是过度设计"的追问。

## 六、与宇通整车 CAN 项目的衔接(面试大杀器)

> 这段要把两个项目串起来讲,展示"方法论复用"能力:

### 6.1 1700帧/s 的量级感受

| 指标 | 数值 | 含义 |
|------|------|------|
| 帧率 | 1700 帧/秒 | 平均每 0.59ms 一帧 |
| 单帧处理预算 | < 0.5ms | 超过即丢帧/积压 |
| 单帧典型 8~16 字节 | 16KB/秒 | 数据量不大,难在"每帧都要处理" |
| 关键 | 处理次数 | 每秒 1700 次解析+写入+可能的业务唤醒 |

### 6.2 方法论迁移(信号级框架如何套用到整车)

| 本项目(仪表/六轴/倒车) | 整车 CAN(1700帧/s) 增强 |
|------------------------|--------------------------|
| 信号注册表 | 按 CAN 报文矩阵(DBC)批量生成注册表(解析 DBC 或代码生成) |
| 单帧解析 | **攒批处理**:收包线程攒 10ms 一批(约17帧)再处理,减少线程切换 |
| 每帧唤醒业务 | **周期发布**:业务按 10ms 周期批量读变化信号,不逐帧唤醒 |
| 超时监控 | 按信号类型分级超时(安全信号更短) |
| 变化检测 version | 消费端按 version 过滤,只处理变化信号 |
| 单锁批量 | 分优先级队列:关键信号(制动/转向)最高优先级立即处理 |
| 预分配 | 固定槽位 + 环形缓冲,零动态内存 |

### 6.3 面试话术(完整版)

> "这套信号级框架是我在天迈项目做的,后来在做整车 CAN(每秒1700帧)时直接复用了这套方法论。
> 1700帧意味着平均每 0.6 毫秒一帧,单帧处理预算不到 0.5 毫秒,不可能每帧都做完整业务。我的方案是:
> 第一,**解析与业务解耦**——收包线程只做'报文拆解+写信号槽',业务按固定周期批量读取,业务永远不阻塞收包;
> 第二,**攒批处理**——收包线程攒一小批(比如 10ms ≈ 17帧)统一处理,减少线程切换和锁竞争;
> 第三,**变化检测**——每个信号带版本号,业务只处理真正变化的信号,避免对相同数据重复计算;
> 第四,**超时与有效性**——状态型信号超时自动失效,业务拿不到陈旧数据,这对安全相关功能尤其重要。
> 这套思路的本质是把 CAN 处理从'逐帧事件驱动'变成'信号状态管理',和 AUTOSAR COM 的信号模型一致。"

## 七、可能被追问的问题(准备答案)

**Q1:为什么不用现成的 SocketCAN / can-utils?**
> 项目跑在车机 SoC 上,数据不是标准 Linux CAN 接口进来的,而是调度子系统通过域通信转发的私有报文(仪表CAN封装、六轴、雷达)。所以需要在应用层自建信号管理。如果是标准 CAN 接口,我也会优先用 SocketCAN + 现成协议栈,再在其上做信号层。

**Q2:信号槽大小怎么定?64 够吗?**
> 本项目信号数量约 20 个,64 留了余量。整车场景可以按报文矩阵实际数量配置(宏可调),或按报文 ID 做两级索引。槽是静态数组,大小是编译期常量,内存固定。

**Q3:锁竞争会不会成为瓶颈?**
> 写路径单锁、临界区只有"拷贝值+时间戳+version",纳秒级;批量更新进一步把锁次数降到 1/N。读路径大部分无锁(只读槽),唯一写 valid 的惰性超时也做了加锁处理(锁内只判超时+置位,回调在锁外),避免与写线程的 valid 竞争。实测在 1700帧/s 量级,锁开销占比可以忽略。

**Q4:超时时间 500ms 怎么定的?**
> 依据数据本身的更新周期:仪表/六轴/倒车一般 20~100Hz,500ms 是更新周期的 5~10 倍,既能容忍偶发丢帧,又能在断链后快速失效。具体值可配置,按信号类型差异化。

**Q5:如果 1700帧/s 时仍有积压怎么办?**
> 三层:①攒批降低处理次数;②消费端按周期+version 只处理变化;③接收侧环形缓冲+丢旧保新(最新状态优先),安全信号单独高优先级队列。
