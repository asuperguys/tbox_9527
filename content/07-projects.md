### 预见性巡航 PCC

**一句话**：基于地图数据（百度/四维图新）感知前方道路信息，经 CAN 下发 CCU，优化动力控制实现节能。

**背景（S）**：宇通客车要降能耗。传统巡航不感知前方路况，坡道、弯道、限速无法提前响应，油耗电耗偏高。

**我的职责（T+A）**：

- **角色**：车端主力/主导，负责 PCC 完整数据链路：接收地图数据 → 解析 → 协议转换 → CAN 下发 CCU
- 百度方案：WebSocket 长连接与云端双向通信，固定频率上报车辆位置（经纬度/航向/速度）；接收坡度、曲率、道路类型、限速，按 ADAS v2 CAN 协议封装周期报文下发 CCU
- 四维图新方案：HTTP 与云控平台对接，获取 SLOPE/STUB/POSITION 报文（坡度、路段桩号、位置），数据对齐与滤波后转发，支持云端 HP 功能
- 可靠性：数据超时判定、丢帧补偿、断线重连（指数退避），云端数据缺失时降级回普通巡航
- 性能：151MB 内存约束下监控 VmRSS/VmData 定位峰值，优化缓冲池与线程模型，避免 OOM、控制 CPU 占用

**技术亮点**：

- 百度 + 四维图新双地图方案并存接入（WebSocket / HTTP 两种通道）
- 151MB 资源受限环境下的内存与 CPU 优化（VmRSS/VmData 监控、缓冲池复用、减少拷贝）
- 超时判定 + 降级策略，保证地图数据缺失时仍安全行车

**结果（R）**：随宇通批量车型上线，稳定运行【补数据：节油率/转发时延/稳定运行天数】

**面试追问 Q&A**：

- **Q：** WebSocket 断线怎么处理？
- **A：** 心跳保活 + 指数退避重连；重连成功后重新上报位置做状态同步；云端数据持续缺失时，超时判定后降级回普通巡航，保证安全。
- **Q：** 两套地图方案为什么并存？差异在哪？
- **A：** 供应商策略不同：百度走 WebSocket 长连接实时交互，四维图新走 HTTP 与云控平台对接；差异主要在数据精度、覆盖范围、协议形式【按实际补充具体对比】。
- **Q：** CAN 报文周期多少？数据怎么防抖/滤波？
- **A：** 【按实际回答具体周期数值】；对坡度、曲率等做数据对齐和滤波后再封装下发，避免抖动值直接进 CAN。
- **Q：** 151MB 内存怎么优化？
- **A：** 监控 VmRSS/VmData 定位内存峰值，缓冲池复用减少频繁申请，减少数据拷贝，控制线程数量，避免 OOM。
- **Q：** 地图数据长时间缺失怎么办？
- **A：** 超时判定 + 降级策略，退回普通巡航，保证行车安全。
- **Q：** 怎么验证功能正确？
- **A：** 台架联调 + 实车路测，与 CCU 联调日志核对报文下发是否符合 ADAS v2 协议。

**1 分钟话术**：

"我在宇通车端项目主导了预见性巡航（PCC）功能开发。原理是：通过地图数据获取前方坡度、曲率、道路类型和限速信息，提前调整车辆动力控制，实现节能。我负责车端完整数据链路——用 WebSocket 和百度云端双向通信、固定频率上报位置、接收地图数据解析后按 ADAS v2 协议走 CAN 发给 CCU；四维图新方案则通过 HTTP 与云控平台对接。终端内存只有 151MB，我通过监控 VmRSS/VmData 做了内存优化，并设计了超时、丢帧补偿和断线重连，保证长时间稳定运行。"

### GNSS 固件升级系统

**一句话**：国产化终端上，用多线程 + 生产者消费者 + CRC32 实现了 GNSS 模块串口固件升级。

**背景（S）**：国产化高性能终端需要支持 GNSS 模块固件在线升级；串口通信容易丢数据、阻塞，升级失败会直接影响终端可用性。

**我的职责（T+A）**：

- **角色**：独立设计并实现升级系统，保证传输可靠、升级可恢复
- 串口通信 + 协议解析
- 多线程架构，生产者-消费者模型分离串口监听与协议处理，避免阻塞和丢帧
- CRC32 校验保障每包完整性
- 升级状态机管理流程：失败重试、异常恢复（断电续刷/回退）

**技术亮点**：

- 生产者-消费者模型解耦串口收发与协议处理，不丢包
- CRC32 逐包校验 + 重发/回退机制，防"半砖"
- 升级状态机 + 断电续刷/回退，升级可恢复

**结果（R）**：升级成功率【补数据：提升至 xx%】

**面试追问 Q&A**：

- **Q：** 为什么用生产者-消费者模型？
- **A：** 串口收包快、处理慢，顺序处理会阻塞导致丢帧；生产者和消费者解耦后，收包线程只管入队，处理线程慢慢消化，不丢数据。
- **Q：** 缓冲区多大？满了怎么办？
- **A：** 【补具体数值】；满了按策略暂停读取或丢弃旧包并告警，保证不覆盖未处理的包【按实际】。
- **Q：** CRC32 校验出错怎么办？
- **A：** 重发该包；重发超限则报错并进入回退流程，保证终端不变成"半砖"。
- **Q：** 升级过程中掉电怎么办？
- **A：** 状态机持久化升级进度，异常恢复支持断电续刷或回退，重启后从断点继续或回到旧版本。
- **Q：** 多线程之间怎么同步？
- **A：** 互斥锁保护共享队列，条件变量/信号量做生产者-消费者通知，避免竞态和忙等。

**1 分钟话术**：

"我在宇通车端项目负责国产化终端的 GNSS 模块固件升级系统。难点是串口通信容易丢数据、阻塞。我采用多线程架构 + 生产者-消费者模型，把串口监听和协议处理解耦，避免丢帧；每包数据用 CRC32 校验保证完整性，出错重发；用升级状态机管理整个流程，支持失败重试和异常恢复，掉电也能续刷或回退，保证升级可恢复。"

### 市场问题分析（eMMC / eSIM / 通信异常）

**一句话**：用数据定位市场终端疑难问题——eMMC 寿命衰减、通信流量异常、故障报文乱发。

**背景（S）**：市场车辆终端陆续出现存储异常/寿命告警，影响整机可靠性与售后成本。

**我的职责（T+A）**：

- **角色**：负责市场疑难问题分析，定位根因并给出可落地的改进方案
- eMMC：采集终端 SMART 与写入量数据，结合写放大系数、磨损均衡机制建立寿命评估模型；定位异常写入源（高频日志落盘、升级包残留等）；通过限制写频次、调整日志策略、优化磨损均衡参数延长寿命
- eSIM（红茶移动）：参与 profile 配置、下载激活联调，处理激活失败、网络切换问题
- 流量异常/故障报文：抓包 + 协议分析定位异常发送源，修复乱发问题

**技术亮点**：

- 基于 SMART + 写放大 + 磨损均衡的 eMMC 寿命评估模型
- 用数据（写入量跟踪、抓包）说话，定位异常源而非拍脑袋
- 覆盖存储、通信、流量三类市场疑难问题，能力可迁移

**结果（R）**：【补数据：覆盖车辆数 / 问题收敛率 / 寿命提升比例】

**面试追问 Q&A**：

- **Q：** eMMC 寿命怎么评估？
- **A：** 写入量 × 写放大系数，与 eMMC 标称耐久（TBW）对比，再结合 SMART 剩余寿命综合评估。
- **Q：** 写放大为什么高？
- **A：** 频繁小写、日志反复落盘、掉电导致数据搬运；我们定位到高频日志落盘、升级包残留等异常写入源。
- **Q：** 怎么验证改进方案有效？
- **A：** 市场回访 + 持续跟踪写入量数据，对比优化前后的写入速率和寿命预测曲线。
- **Q：** eSIM 激活失败怎么排查？
- **A：** 检查 profile 状态与下载激活流程、网络和 APN 配置，与红茶移动联调看激活日志，定位是平台侧还是终端侧问题。
- **Q：** 流量异常/故障报文乱发怎么定位？
- **A：** 抓包 + 协议分析，统计发送频率和报文内容，定位异常发送源（哪个模块/进程），修复后持续观察是否收敛。

**1 分钟话术**：

"我负责市场终端疑难问题的数据化分析。一是 eMMC 寿命衰减：采集 SMART 和写入量数据，结合写放大系数和磨损均衡机制建立寿命评估模型，定位到高频日志落盘等异常写入源，通过限制写频次、调整日志策略延长寿命；二是 eSIM 集成联调，处理激活失败、网络切换问题；三是通信流量异常，通过抓包和协议分析定位异常发送源并修复。这类问题直接降低了售后成本，也体现了我的数据定位能力。"

- **Q：** 升级失败一般分几类？
- **A：** 四类：下载失败（网络/断点）、验签失败（包损坏/证书）、刷写失败（通信/时序）、版本校验失败；排查时按链路分段定位。

- **A：** 下载进度和状态持久化到 NVRAM，重启后从断点继续，不用重头下载。
- **Q：** 升级状态机有哪些状态？
- **A：** 空闲、检查、下载、暂停、升级、预安装等，崩溃后能从持久化的状态恢复。
- **Q：** 为什么刷写要 34/36/37？
- **A：** 34 请求下载建立会话，36 传输数据，37 请求退出结束传输，配合 27 安全访问解锁刷写权限。
- **Q：** 你在 OTA 里的角色是什么？

### 行为面试与 HR 常见问题

**1. 为什么离开现在公司？外包身份怎么解释？**

> 应答要点：先肯定当前积累——"我在宇通车端项目驻场 2 年，完整负责了 PCC 功能与市场问题分析，希望加入正编团队长期发展"；不回避、不强调外包，落脚点放在"想长期稳定发展"。

**2. 为什么从杭州图软来郑州？为什么选择郑州？**

> 应答要点：家庭/生活规划在郑州，郑州车联网和汽车电子公司越来越多，想长期在郑州发展；突出稳定性，别谈"杭州待不下去"这类负面理由。

**3. 你最有成就感的一件事是什么？**

> 应答要点：首选 PCC——从 0 到 1 主导双地图方案接入并随宇通批量车型上线；备选市场问题分析——用数据定位 eMMC 寿命问题，直接降低售后成本。先讲结论和数据，再讲过程。

**4. 遇到不会的技术问题怎么办？**

> 应答要点：按"先复现 → 抓日志 → 定位 → 验证"的排查思路；查文档/源码，必要时请教同事，独立解决后沉淀成文档，形成自己的排查经验。

**5. 和驻场方（宇通）或同事有分歧怎么处理？**

> 应答要点：先对齐目标和事实，用数据说话而不是争对错；必要时升级沟通。举例：市场问题分析中靠写入量数据说服对方【按实际准备一个案例】。

**6. 能接受加班和出差吗？**

> 应答要点：能。驻场和 3000 台交付支持阶段都有过连续加班和出差；以任务完成为目标，同时注重效率，靠机制和文档避免重复加班。

**7. 期望薪资和到岗时间？**

> 应答要点：郑州 3-5 年嵌入式 Linux/车联网岗位参考 12-18k，结合公司平台和岗位职责面谈；到岗时间按实际情况回答（简历写"面议"）。

**8. 你的缺点是什么？**

> 应答要点：选一个真实但不致命的缺点并给出改进动作——例如"面对全新领域容易先自己埋头啃，现在会先确认关键路径、再向有经验的人对齐再动手"，展示自我认知和成长性。
