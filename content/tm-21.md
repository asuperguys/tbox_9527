## 一、当前实现的三个根本缺陷(先批判自己,展示深度)

### 缺陷1:瞬时值直接判定,没滤波
```cpp
// 当前:RapidAccEventProcess → dealSharpSpeedChanged
float diffAbs = std::abs(values[LineAccIndex] - balanceAcc);  // 瞬时差
if (diffAbs >= mSensorCfg_Jijia.detectTHD) ...                // 直接超阈值
```
**问题**:路面颠簸是高频冲击(10Hz+),车辆加减速是低频(<2Hz)。不区分频率,一次颠簸就可能误报。

### 缺陷2:重力分量当固定基准,忽略姿态变化
```cpp
// 当前:getPredictValue 用静止时重力分量做平衡值
mPredictLinearAcc = mPreLinearAcc + mPreAvgDiff;
```
**问题**:刹车时车头下沉(俯仰)、转弯时侧倾 → 传感器坐标系随车身转动,重力投影变化。
**急刹瞬间俯仰 2~3° 的重力投影变化 ≈ g·sin(3°) ≈ 0.5m/s²,与真实急刹车加速度同量级**——不补偿必误报。这是最大误报源。

### 缺陷3:急转弯只看角速度,没用横向加速度
```cpp
// 当前:只看陀螺仪Z轴角速度
if (std::abs(tmpValues[index]) >= 角度阈值) ...
```
**问题**:危险程度 = 横向加速度 = **车速 × 角速度**。低速大转角不危险、高速小转角才危险。只比角速度:漏报高速小幅急转、误报低速大转。

### 缺陷4:瞬时触发,无"持续时间/占空比"判定
只有上报间隔过滤(防刷屏),没有"事件持续多久才算成立"——100ms 的加速度尖峰就被判急加速。

### 缺陷5:无滞回
进入/退出同阈值,信号在阈值附近抖动反复触发。

## 二、物理模型:为什么"横向加速度=车速×角速度"是准判据

### 转弯物理
- 车辆转弯时做圆周运动,向心(横向)加速度:`ay = v²/R = v × ωz`
- `ωz` = 横摆角速度(陀螺仪Z轴),`v` = 车速
- **这是危险度的物理量**:同样角速度下,车速越高越危险

### 纵向物理
- 加速度计测的是 `a = a_real + g·(重力投影)`
- 重力投影随姿态变化:`投影 = g·sin(pitch/roll)`
- 要得到真实运动加速度,必须**减去重力投影** → 需要姿态估计

### 频率分离
- 车辆运动(加减速/转弯):< 2Hz
- 路面颠簸/冲击:> 10Hz
- 低通滤波(截止~5Hz)天然分离

## 三、完整设计(信号链路)

```
六轴原始数据
  │
  ├─ 陀螺仪(ωx,ωy,ωz) ──▶ 低通滤波 ──▶ 姿态估计(互补滤波) ──┐
  │                                                       │
  ├─ 加速度计(ax,ay,az)─▶ 低通滤波 ──▶ 重力投影补偿 ──────▶ 真实纵向加速度 ax'
  │                                                       │
  ├─ 车速(仪表CAN) ──────────────────────────────────────▶ 横向加速度 ay = v×ωz
  │
  ├─▶ 判定模块1:急加速/急减速(ax' + 时间窗口/占空比 + 滞回)
  ├─▶ 判定模块2:急转弯(|ωz| 或 ay + 时间窗口 + 滞回)
  └─▶ 耦合抑制:转弯时抑制纵向判定(向心加速度污染)
```

### 模块1:低通滤波
```cpp
// 一阶低通,截止~5Hz(车辆运动<2Hz,颠簸>10Hz)
float lowPass(float raw, float prev, float alpha /*0.3~0.5*/) {
    return alpha * raw + (1 - alpha) * prev;
}
```

### 模块2:互补滤波姿态估计 + 重力补偿(核心)
```cpp
// 互补滤波:加速度计给低频姿态(长期准),陀螺仪给高频姿态(短期准)
pitch = A * pitch_acc + (1-A) * (pitch + gyro_y * dt);
roll  = A * roll_acc  + (1-A) * (roll  + gyro_x * dt);

// 加速度计直接算姿态(静止/匀速时准)
pitch_acc = atan2(-ax, sqrt(ay*ay + az*az));
roll_acc  = atan2(ay, az);

// 减去重力投影 → 真实运动加速度
float ax_real = ax - g * sin(pitch);   // 纵向(车头方向)
float ay_real = ay - g * sin(roll);    // 横向
```

### 模块3:急加速/急减速判定(时间窗口+占空比+滞回)
```cpp
typedef struct AccJudger_st {
    float thdHigh;    // 进入阈值(如 2.5 m/s²)
    float thdLow;     // 退出阈值(如 1.5 m/s²,滞回)
    float windowMs;   // 时间窗口(如 2000ms)
    int   dutyRation; // 占空比阈值(如 70%)
    int   overCnt, totalCnt;
    bool  active;
} AccJudger_t;

void update(AccJudger_t& j, float acc, bool speedValid) {
    if (!speedValid) return;
    j.totalCnt++;
    if (acc > j.thdHigh) j.overCnt++;          // 或 acc < -thdHigh(急减速)
    if (j.totalCnt >= j.windowMs / 20) {        // 20ms 采样周期,窗口满
        float duty = (float)j.overCnt / j.totalCnt * 100;
        if (duty >= j.dutyRation) { if(!j.active) /*触发*/; j.active = true; }
        else if (duty < j.dutyRation - 10) { if(j.active) /*结束*/; j.active = false; } // 滞回
        j.totalCnt = j.overCnt = 0;             // 窗口滑动
    }
}
```

### 模块4:急转弯判定(双判据)
```cpp
float ay_from_gyro = speed_to_ms(speed) * omega_z;  // 横向加速度

// 判据A:角速度超阈值(如 >15°/s)
// 判据B:横向加速度超阈值(如 >4 m/s² ≈ 0.4g)
bool sharpTurn = (fabs(omega_z) > turnThdOmega) || (fabs(ay_from_gyro) > turnThdAy);
// 方向:omega_z > 0 左转,< 0 右转
```
> 低速大转角:角速度大但横向加速度小 → 判据B抑制,不误报;
> 高速小转向:角速度小但横向加速度大 → 判据A+车速弥补,不漏报。

### 模块5:耦合抑制与交叉验证
```cpp
// 转弯时向心加速度污染纵向轴 → 转弯中挂起急加减速判定
if (isSharpTurning) { 挂起急加减速判定; }
// 交叉验证:急加速车速应上升,急减速应下降(用仪表CAN车速)
bool speedConsistent = (急加速 && speedRising) || (急减速 && speedFalling);
// 可选:刹车信号(仪表CAN)辅助确认急减速
```

## 六、面试话术(完整版)

> "当前实现是'瞬时值超阈值'直接判定,我分析有三个不准确来源:一是没滤波,路面颠簸直接进判定;二是把重力分量当固定基准,没考虑刹车点头/转弯侧倾导致的姿态变化;三是急转弯只看角速度,没用'横向加速度=车速×角速度'这个物理量。
> 我的改进是:先低通滤波区分运动和颠簸;用互补滤波做姿态估计,从加速度计读数里减去重力投影,得到真实纵向加速度;急加减速用'时间窗口+占空比+滞回'判定,急转弯用'角速度+横向加速度'双判据,再用车速做交叉验证、转弯时抑制纵向判定防止向心加速度污染。
> 这样能在颠簸、俯仰、侧倾耦合的工况下,只对真实的三急事件报警。"

## 七、可能追问与应答

**Q:互补滤波的计算量在嵌入式够吗?**
> 就几个 atan2/乘加,50Hz 下微秒级,嵌入式完全够;比完整卡尔曼(矩阵运算)轻量得多,是姿态估计的经典折中。

**Q:为什么不用卡尔曼?**
> 卡尔曼更优但计算量/调参复杂度高。互补滤波在"加速度计低频准+陀螺仪高频准"这个场景下性能接近,实现简单、无矩阵求逆,适合 MCU/SoC 应用。

**Q:阈值 2.5 m/s² 怎么来的?**
> 参考公交运营规范(急加速/急减速判定标准)+ 实测标定;进入阈值高、退出阈值低形成滞回。可配置化,不同车型微调。

**Q:停车时会不会误报?**
> 车速无效(≤0或超时)不判定——这是第一道门;停车时只有晃动,低通滤波+占空比过不了。

**Q:和现有代码怎么衔接?**
> 保持对外接口不变(extern_GetSixAxisSensorData → SixAxisSensorDataParse → 三急处理),内部替换判定逻辑;数据源入口当前在 unixprotocol 被注释,接入时一并恢复。

### 落地时的工程细节(面试讲"我踩过并解决的坑")

1. **M_PI 兼容性**:`M_PI` 不是 C/C++ 标准宏,部分嵌入式工具链(严格 `-std=c++11`/ARM 编译器)未定义会导致编译失败。
   → 用 `#ifndef TU_PI / #define TU_PI 3.14159...f` 自定义,避免平台差异。
2. **姿态初值**:互补滤波 A=0.02 收敛慢,坡道停车时姿态要很久才准。
   → 首次调用直接用加速度计姿态初始化(`atan2` 直接算),立即可用,后续再互补融合。
3. **判定互斥(已修复)**:初版急减速统计被 `if(!m_accActive)` 门控——急加速窗口未满/刚触发期间,急减速窗口计数被抑制,可能导致急加速后紧跟的真实急减速漏报(单测用例4会FAIL)。
   → 改为**急加速/急减速独立统计、触发时互斥**(各自用 active 标记去重,不再互相阻塞)。
   → 单测新增 **用例4b 回归用例**(急加速→急减速,验证修复);README 记为 8 类用例。
4. **时间基准**:节流用内部累计 dt,首帧用标志位处理,避免依赖外部时钟。

> 这些细节面试时可主动讲:"落地时我处理了三个工程细节——M_PI 平台兼容、姿态初值收敛、判定互斥;其中判定互斥还修过一个真 bug:急加速期间急减速统计被抑制会导致漏报,我改成独立统计+触发互斥,单测用例(急加速后紧跟急减速)也验证了这个场景。"
