# 09 · 优化建议与技术亮点清单

> 面试加分项:展示你不只是"会写代码",还会**发现问题、规划优化**。
> 主动提出"我发现并梳理了这些问题"比被问到时才答,效果完全不同。
> 建议从清单中选 **3~5 个**作为你的"我发现的问题",能讲清"问题是什么+影响+怎么改"即可。

## 一、最值得讲的 5 个问题(建议优先掌握)

### 1. 三急"急加速/急减速"报警未生效(你的模块,最安全)
- **问题**:three_urgent_process.cpp 中 `dealWarnEvent` 的调用被注释(204/210行),急转弯生效但急加速/急减速只打日志不报警;`sharpSpeedEventDataProcess` 全局封装是空实现。
- **影响**:平台收不到急加速/急减速事件,三急只有一项可用。
- **改法**:恢复 dealWarnEvent 调用 + 实现 sharpSpeedEventDataProcess 封装 + 确保 external_data_process.cpp 中 `sharpSpeedEventDataProcess(lineData)` 取消注释。
- **面试价值**:这是你负责模块的"已知缺口",主动提出来说明你对自己做的部分有完整认知。

### 2. 报警上传校验逻辑恒为假(协议层,展示你懂协议)
- **问题**:ti_protocol_manager.cpp:1080 `(SUN_ALARM_BSD > data[0]) && (data[0] > SUB_ALARM_REVERSE)` 即 `data[0]<0x63 && data[0]>0x69`,恒为假,非法报警ID不会被拦截。
- **改法**:应为 `||` 或枚举判断 `if(data[0]!=0x63 && !=0x64 && !=0x65 && !=0x66 && !=0x67 && !=0x69)`。
- **面试价值**:说明你真读过协议层代码,能发现逻辑bug。

### 3. 空指针解引用会崩溃(协议层)
- **问题**:ti_protocol_manager.cpp:1079 `if(nullptr==data||len<=0){ LogWarn(..., data[0]); return -1; }` —— data为空时仍访问data[0]打日志,必崩。
- **改法**:先判空再打日志。
- **面试价值**:经典空指针问题,展示代码审查能力。

### 4. 参数映射错配(你的模块,展示你懂参数体系)
- **问题**:safety_para_manager.cpp 中 ADAS 报警映射错乱:
  - 0x6401前向碰撞 误绑到 E_ADAS_LANDEPARTURE_CONF(车道偏离)
  - 0x6402车道偏离 误绑到 E_ADAS_FORCRASH_CONF(前向碰撞)
  - DMS分心误用哈欠conf、打哈欠/闭眼action落库字段颠倒
- **影响**:平台下发参数时写错字段,报警联动动作错乱。
- **改法**:逐条核对 AlarmType_e 与 SafetyPara_e 的对应关系。
- **面试价值**:你对参数ID体系了如指掌才能发现。

### 5. 算法激活失败仍返回成功(算法层,展示你懂算法对接)
- **问题**:alg_api_ARC.cpp:788 ALG_activateSDK 无论成败都 return 0,上层误判激活成功,接着初始化必然失败。
- **改法**:激活失败返回<0,上层根据返回值决定是否重试/报警。
- **面试价值**:激活流程是你掌握算法抽象层的体现。

## 三、可展示的技术亮点(你负责部分的正向价值)

> 除了"发现bug",还要讲"我做得好的设计"。以下每个都能展开成小故事。

### 亮点A:参数注册表(配置驱动开发)
> "几百个参数,我用一张注册表管理,每个参数一行注册(表名/字段/类型/默认值/解析/通知),新增参数零侵入,平台下发、App设置、默认值三路数据流统一收口。这是配置驱动开发思想的落地——代码的扩展点从'改if-else'变成'加一行数据'。"

### 亮点B:三层过滤的信号处理思路(三急)
> "传感器数据噪声大,我用'抖动阈值→事件阈值→时间间隔'三层过滤,再用滑动均值处理温漂、平衡值预测分离重力分量。这套'先滤波再判定'的思路可以迁移到任何传感器类应用。"

### 亮点C:安装方向自适应
> "设备装在不同车辆上朝向不同,我用数据库配置驱动轴向选择,换车不用改代码。这解决了嵌入式产品'安装工艺差异'导致的适配问题。"

### 亮点D:变更计数驱动联动
> "参数变更后算法需要重载,但重载=算法重启,不能频繁触发。我用变更计数判断参数是否真的变了,变了才重载,避免无效重初始化。"

### 亮点E:ini文件变化检测
> "UI跨进程读算法状态,我做了变化检测(快照对比,变了才写),避免每秒无条件写文件磨损flash。嵌入式里IO和flash寿命是真实约束。"

### 亮点F:车速来源优先级设计
> "车速是算法判定的关键输入,我设计了'测试后门→仪表CAN→GPS'三级优先级,仪表优先因为GPS在遮挡环境不准,测试后门方便现场模拟。"

### 亮点G:CAN信号级重构(完整落地案例,详见[11 文档](#/tm-11))
> "我实际完成的一次重构:把外部数据模块从'帧级解析'升级为'信号级处理'(信号注册表+信号槽+超时监控+批量更新+变化检测),解决了高频数据下字段误清、数据陈旧、收包阻塞三大问题;对外接口不变+独立单测+原文件备份控制回归风险。这套方法论直接迁移到宇通整车CAN(1700帧/s)项目。"

## 四、面试怎么用这份清单

### 主动展示(推荐)
> 面试官问"项目里有没有遇到什么问题/有没有可以改进的地方"时:
> "我梳理代码时发现了一些问题。比如我负责的三急模块,急加速急减速的报警触发其实是被注释掉的,只生效了急转弯,这个我后续在推进补全。另外我在读协议层代码时发现报警上传的子事件校验逻辑写反了,非法ID拦不住……"
> 讲2-3个,每个30秒,展示"会发现问题+懂全局"。

### 被追问时
> 面试官问"如果让你优化这个项目,你会从哪开始":
> "我会分优先级:第一优先是正确性问题,比如激活失败误判成功、报警校验恒为假、空指针崩溃这些;第二是功能补全,比如急加速急减速上报、0x8505查询应答;第三是健壮性,比如共享状态加锁、去掉遗留调试打印;第四是可配置化,把硬编码的标定和阈值改成读数据库。"

### 怎么讲"优化"不显狂妄
> 用"我梳理时发现""我理解的改进方向""如果我来做会优先"这种措辞,展示思考而非批评。
