## 车载协议与 OTA

> 车载工程师区别于普通嵌入式工程师的核心，在于"协议栈 + 诊断 + 刷写"这一整套体系。面试官常从 CAN 帧一路追问到 CAN TP、UDS、DoIP、OTA，考察的不只是背协议号，而是你在真实项目里如何解析报文、如何定位刷写与升级故障。这部分是 T-Box 岗位的必考盘，也是你"懂车"的直接证据。

### CAN 帧结构与报文解析

**一句话要点**：标准帧 11 位 ID，扩展帧 29 位 ID；仲裁靠 ID + RTR 逐位比较，ID 越小优先级越高，数据帧（RTR=0）优先于远程帧；位填充规则是连续 5 个相同位后插入 1 个反相位，用于接收同步与错误检测。
**面试怎么问**：CAN 报文如何区分数据帧和远程帧？两帧同时发送时谁赢得仲裁？什么是位填充，作用是什么？
**用例 / 示例**：
```text
标准数据帧：SOF | ID(11bit) | RTR | IDE | r0 | DLC(4bit) | DATA(0-8B) | CRC(15bit) | ACK | EOF
示例：0x18FF50E5  8  01 02 03 04 05 06 07 08
      ID=0x18FF50E5（29位扩展帧）, RTR=0（数据帧）, DLC=8
      J1939 风格解读：优先级3 | PGN=0xFF50 | 源地址=0xE5

远程帧（RTR=1，无数据段）：0x123  0   ← 只发请求不带数据，用于让对端发送指定报文
仲裁要点：总线空闲同时发送时，每位比较，显性位(0)赢隐性位(1)，所以 ID 小者优先
```
**关联项目**：预见性巡航（ADAS v2 协议经 CAN 下发 CCU）、通用基础

---

### CAN FD 特点

**一句话要点**：CAN FD 保留仲裁段（最高 1 Mbps 与经典 CAN 兼容），数据段通过 BRS 位切换可提速至 5~8 Mbps，单帧数据最多 64 字节；CRC 升级为 17/21 位，可靠性更高。
**面试怎么问**：CAN FD 相比经典 CAN 快在哪？BRS 位的作用是什么？CAN FD 节点能不能和经典 CAN 节点混跑？
**用例 / 示例**：
```text
CAN FD 帧：SOF | 仲裁段(11/29bit ID) | FDF | BRS | ESI | DLC | DATA(0-64B) | CRC(17/21bit) | ACK | EOF
示例：ID=0x1AA  64  xx...(64字节大数据)
      FDF=1 表示 FD 帧；BRS=1 表示数据段切换高速率；ESI=1 表示发送节点处于错误被动

典型场景：UDS 多帧下载、网关/记录仪大数据透传（一帧顶经典 CAN 八帧，大幅降低总线占用）
注意：FDF=0 的经典帧 CAN FD 控制器可正常收发；FD 帧不能发给纯经典 CAN 节点
```
**关联项目**：通用基础（T-Box 网关/数据转发）、云公交一体机（大数据链路）

### CAN TP（ISO 15765-2）

**一句话要点**：单帧（SF）最多带 7 字节数据（1 字节 PCI 开销）；超过则用首帧（FF）声明总长度、连续帧（CF）传数据、流控（FC）控制节奏；接收端按 PCI 中的长度与序号重组完整报文。
**面试怎么问**：UDS 响应超过 8 字节怎么发？首帧里 12 位长度表示什么？流控帧里的 BS 和 STmin 分别管什么？
**用例 / 示例**：
```text
单帧 SF：PCI[0x0N=数据长度] + DATA(≤7B)
         07 01 02 03 04 05 06 07        → 7 字节数据

首帧 FF：PCI[0x10|长度高4位][长度低8位] + 前6字节数据
         10 14 62 F1 90 01 02 03        → 总长 0x014=20 字节

流控 FC：PCI[0x30|FS] [BS] [STmin]
         30 08 14                       → FS=0 继续发；BS=8 每块8帧；STmin=0x14=20ms

连续帧 CF：PCI[0x20|SN] + 7字节数据，SN 从 1 递增，0x0F 后回绕到 0x00
         21 xx...  22 xx...  23 xx...
```
重组逻辑：收到 FF 记录总长并回 FC → 按 SN 收齐所有 CF → 校验字节数一致才算完整；超时/错序按协议超时处理。
**关联项目**：OTA 排查支持（UDS 刷写底层就是多帧传输）、预见性巡航

### UDS 诊断服务总览（ISO 14229）

**一句话要点**：UDS 是应用层诊断协议，经 CAN TP 承载；核心服务：10 会话控制、22/2E 读写、27 安全访问、31 例程、3E 心跳、11 复位、14 清故障、19 读故障、28/85 通信与故障码控制；负响应统一为 7F + SID + NRC。
**面试怎么问**：刷写固件一般要进哪个会话？NRC 0x78 是什么含义？19 服务常用子功能有哪些？
**用例 / 示例**：
```text
请求：02 10 02                → 进入编程会话(0x02)
响应：06 50 02 00 32 01 F4    → 0x50 表示成功，后带会话参数(P2/P2* 时间)

请求：03 22 F1 90             → 按 DID 读数据(0xF190)
响应：06 62 F1 90 01 02 03 04 → 读到 4 字节

负响应：03 7F 22 31            → 0x7F + 原SID + NRC
常见 NRC：0x10 一般拒绝 / 0x11 服务不支持 / 0x13 长度或格式错误
          0x22 条件不满足 / 0x31 请求超范围 / 0x33 安全访问拒绝 / 0x78 响应挂起(继续等待)
```
记忆口诀：10 会话 22/2E 读写、27 安全 31 例程、3E 保活 11 复位、14 清码 19 读码、28 通信 85 控码。
**关联项目**：OTA 排查支持（刷写与诊断报文分析）、主动安全系统

### UDS 安全访问 27

**一句话要点**：奇数级别请求 seed（0x27 01）→ ECU 返回随机 seed → 用保密算法算出 key（0x27 02 回发）→ 校验通过后解锁写权限；防暴力破解靠每次 seed 不同 + 尝试次数上限 + 失败延时锁定。
**面试怎么问**：27 服务怎么防重放攻击？key 算法一般保存在哪里？为什么 27 成功后才能做 2E 写？
**用例 / 示例**：
```text
请求：06 27 01 00 00 00 00    → 请求 seed（级别01，奇数=请求）
响应：06 67 01 12 34 56 78    → seed = 0x12345678（4字节）

本地计算 key = f(seed)，例如简单异或：key = 0x12345678 ^ 0xA5A5A5A5 = 0xB791F3DD

请求：06 27 02 B7 91 F3 DD    → 回发 key（级别02，偶数=发送）
响应：02 67 02                 → 解锁成功
失败：03 7F 27 35              → 0x35 key错误 / 0x36 超次数 / 0x37 延时未到
```
关键点：seed 每次不同（防重放）；算法存放在安全区/HSM 中，报文中只传结果不传算法；连续失败 N 次锁定并延时。
**关联项目**：OTA 排查支持（刷写前安全访问失败是常见故障点）、通用基础

### 34/36/37 固件下载流程

**一句话要点**：0x34 请求下载（声明地址与长度）→ 0x36 按块传数据（块序号 1~255，0xFF 后回 0x00）→ 0x37 请求退出传输；刷写后 ECU 校验完整性、写签名，失败则整包作废。
**面试怎么问**：0x36 的块序号到 0xFF 之后怎么办？为什么下载前要先擦除 Flash？刷写完成后怎么确认固件正确？
**用例 / 示例**：
```text
请求下载：0B 34 00 44 00 00 10 00 00 00 80 00
          长度0x0B | 34 | 00(数据格式:不压缩不加密) | 44(地址4B+长度4B)
          | 地址 0x00001000 | 长度 0x00008000
响应：   04 74 20 20 00     → 每块最大长度 0x2000（8192）字节

传输数据：09 36 01 xx xx xx xx xx xx xx   → 块序号 1
         09 36 02 xx xx xx xx xx xx xx    → 块序号 2（0xFF 后回到 0x00 继续）
响应：   02 76 01                          → 每块回 0x76 + 块序号

退出传输：01 37              → 响应 01 77
校验：   31 01 02 01 <地址><长度>  → 例程控制检查内存（可选步骤）
```
流程注意：进编程会话 → 安全访问 → 34（隐含擦除）→ 36 分块 → 37 结束 → 校验/写版本 → 复位；任一环节 NRC 都要能定位（0x31 地址越界、0x78 超时挂起等）。
**关联项目**：GNSS 固件升级（实际 UDS 刷写实现）、OTA 排查支持

### DoIP（ISO 13400）

**一句话要点**：以太网诊断：车辆发现与路由激活走 UDP 13400，诊断报文走 TCP 13400；流程为车辆公告/识别 → TCP 连接 → 路由激活 → 收发 0x8001 诊断消息（加分项：ISO 13400-2:2019 已把端口改为 3496）。
**面试怎么问**：DoIP 为什么分 TCP 和 UDP 两个通道？车辆发现流程是怎样的？诊断消息报文里 SA/TA 是什么？
**用例 / 示例**：
```text
UDP 13400：
  车辆识别请求(广播)  → 0x0001  VIN+EID+GID
  车辆公告            → 0x0004  （节点上线主动广播）
  路由激活请求        → 0x0005  激活类型(默认 0x00)
  路由激活响应        → 0x0006  激活码 0x00=成功
  激活检查            → 0x0007  Alive Check（保活）

TCP 13400：
  诊断消息            → 0x8001  SA(源逻辑地址) + TA(目标逻辑地址) + UDS 数据
  例：测试仪 0x0E00 → ECU 0x0E80，数据 10 02 进入编程会话
```
流程：车辆上线公告 → 测试仪 UDP 识别车辆 → TCP 连接 13400 → 路由激活 → 发 0x8001 诊断消息 → 会话结束断开。
**关联项目**：OTA 排查支持（整车以太网刷写链路）、通用基础

### SOME/IP 简介（概念级）

**一句话要点**：SOME/IP 是车载以太网的面向服务通信中间件，服务发现（SD）走 UDP 30490，通过 Offer/Find/Subscribe 完成发现与订阅；报文头固定 16 字节：Message ID（服务ID+方法ID）、Length、Request ID、协议/接口版本、消息类型。
**面试怎么问**：SOME/IP 与 CAN 信号通信的本质区别？服务发现为什么用 UDP？序列化里 Length 字段为什么重要？
**用例 / 示例**：
```text
SOME/IP 报文头（固定16字节）：
  Message ID(4B) | Length(4B) | Request ID(4B)
  | Protocol Ver(1B) | Interface Ver(1B) | Message Type(1B) | Return Code(1B)

  Message ID = Service ID(16bit) << 16 | Method ID(16bit)
  消息类型：0x00 REQUEST / 0x01 REQUEST_NO_RETURN / 0x02 NOTIFICATION / 0x80 RESPONSE / 0x81 ERROR
  Length = 从 Request ID 到报文尾的长度（不含 Message ID 和 Length 自身）

服务发现(SD)：
  OfferService  服务提供方上线广播
  FindService   请求方查找服务
  SubscribeEventgroup  订阅事件组（用于周期/事件通知）
```
序列化要点：每个元素前带长度前缀（TLV 风格），解析时按长度跳过未知字段，保证前后版本兼容——这是面试常问的"为什么要带 Length"。
**关联项目**：通用基础（T-Box 网关新架构演进方向）

### OTA 升级链路全流程（排查视角）

**一句话要点**：云端下发 → 下载（断点续传）→ 完整性校验 → 验签 → 解密 → UDS 刷写（进编程会话→安全访问→34/36/37）→ 版本校验 → 提交/回滚；排查时按"卡在哪一环"定位，每阶段有独立日志与状态码。
**面试怎么问**：OTA 升级失败，你的排查思路是什么？升级到一半断电怎么办？怎么防止刷错版本？
**用例 / 示例**：
```text
全链路状态机：
  等待下载 → 下载中(断点续传) → 完整性校验(SHA256) → 签名校验(RSA/ECC)
  → 版本检查 → 进编程会话(10 02) → 安全访问(27) → 34/36/37 刷写
  → 刷写校验(31 检查/回读) → 写升级状态标记 → 复位 → 上报新版本 → 提交
  任一步失败 → 按回滚策略恢复旧版本/旧分区

排查思路（维护排查视角，现场实战）：
  1. 查升级状态码 + 阶段日志，先定位失败环节（下载?刷写?校验?）
  2. 下载失败 → 看网络、磁盘空间、续传点是否有效
  3. 刷写失败 → 抓 UDS 报文看 NRC：0x33 安全访问失败 / 0x31 地址越界 / 0x78 超时
  4. 校验失败 → 比对包哈希、确认分区是否写对
  5. 回滚触发：连续 N 次启动校验失败、升级标志位未提交、关键校验不过
```
注意：本工程师在 OTA 项目中的角色是**维护与排查**——面试重点是"能讲清链路、有定位方法论、能读现场日志"，不要强调开发过 OTA 客户端。
**关联项目**：OTA 排查支持（核心）、市场问题分析（eMMC 与 OTA 写入相关）

### 断点续传与状态持久化

**一句话要点**：下载和刷写都做成状态机，把阶段、字节偏移、块校验值持久化到 NVRAM/文件，崩溃重启后从断点恢复；状态文件用"临时文件 + 原子改名 + fsync"写入，避免掉电写坏。
**面试怎么问**：升级到一半断电重启，怎么做到不从头再来？状态文件本身写坏了怎么办？为什么用 rename 而不是直接写原文件？
**用例 / 示例**：
```c
// 升级状态结构体：下载阶段的关键持久化数据
typedef struct {
    uint32_t magic;         // 魔数，校验结构有效性
    uint8_t  phase;         // 0=IDLE 1=下载中 2=校验中 3=刷写中 4=已提交
    uint32_t offset;        // 已下载字节偏移（断点续传）
    uint8_t  chunk_sha[32]; // 上一块哈希，续传前先校验
    uint8_t  retry_cnt;     // 重试次数，超限触发回滚
    uint32_t crc32;         // 结构自身校验
} ota_state_t;

// 原子写：先写 .tmp 再改名，防止写一半掉电留下坏文件
snprintf(tmp, sizeof(tmp), "%s.tmp", STATE_FILE);
write_state_to(tmp, &st);   // 写临时文件
fsync(fd);                  // 刷盘，确保数据落盘
rename(tmp, STATE_FILE);    // 原子替换，要么旧要么新
```
重启流程：上电读状态 → 校验 magic/crc → 按 phase 恢复（下载中→续传；刷写中→查回滚标志）→ 状态损坏则走保守策略（重新下载或回滚）。
**关联项目**：OTA 排查支持（断点续传故障定位）、GNSS 固件升级（升级状态机）

### eSIM：LPA / SM-DP+ / Profile 下载激活

**一句话要点**：eSIM 把 SIM 卡固化为 eUICC 芯片，运营商 profile（卡数据）通过 LPA 从 SM-DP+ 远程下载安装；LPA 管本机 profile 生命周期，SM-DP+ 是远程配置平台，下载后需 enable 才生效。
**面试怎么问**：eSIM 和传统 SIM 的本质区别？profile 下载激活的完整流程？多 profile 场景下切换运营商要注意什么？
**用例 / 示例**：
```text
profile 下载激活流程（GSMA SGP.22 消费类 / SGP.02 M2M）：
  1. 终端获取 SM-DP+ 地址（默认 profile / 扫码 / 服务器下发）
  2. LPA 与 SM-DP+ 建立 HTTPS 安全通道（证书双向认证）
  3. ES10b.InitiateProfileDownload 发起下载（LPA↔eUICC）
  4. profile 数据经加密通道下发并安装到 eUICC
  5. enable 新 profile，切换/注销旧 profile
  6. 模组重新搜网注册，业务恢复

profile 生命周期：Disabled → Enabled → Disabled → Deleted
关键点：同一时刻只有一个 profile 处于 Enabled；下载需运营商侧放号（SM-DP+ 预置/推送）
```
T-Box 场景：eSIM 免换卡实现多运营商切换与产线写号，适合车联网跨境/多运营商网络，故障排查时关注 profile 状态、SM-DP+ 地址可达性、证书有效期。
**关联项目**：红茶移动 eSIM 项目（云公交一体机 eSIM 方案）、市场问题分析（eSIM 相关故障）

### eMMC 寿命分析

**一句话要点**：eMMC 寿命由擦写次数决定，写放大（WA）= 实际写入 Flash 数据量 ÷ 主机写入数据量，磨损均衡与垃圾回收（GC）决定寿命表现；健康度看 SMART/健康报告（平均擦除次数、最大擦除次数、磨损指示）。
**面试怎么问**：写放大是怎么产生的，怎么降低？eMMC 掉电有什么风险？排查存储寿命问题时你收集哪些数据？
**用例 / 示例**：
```text
写放大来源：映射表更新、GC 搬移、日志频繁追加写、小文件碎写、掉电后数据重建
降低手段：日志批量落盘、分区对齐、减少元数据更新、掉电保护（PLP）

eMMC 健康指标（健康报告/SMART，JEDEC）：
  Average Erase Count   平均擦除次数
  Max Erase Count       最大擦除次数（热点块）
  Wear Indicator        磨损指示（0~100%）
  寿命估算 ≈ 容量 × 标称P/E次数 ÷ (每日写入量 × 写放大)

真实排查案例思路（市场问题分析 eMMC-eSIM 专项）：
  现象：批量设备卡顿/变砖
  ① 读健康报告，看擦除次数分布是否出现热点块
  ② 对比正常设备基线，确认是否异常偏高
  ③ 抓写入日志定位异常写源（日志风暴 / 频繁 OTA / 缓存策略不当）
  ④ 结合 OTA 频率与写放大系数估算寿命余量
  ⑤ 结论落为固件优化（减写次数）或硬件方案调整
```
**关联项目**：市场问题分析（eMMC-eSIM 专项）、OTA 排查支持（刷写本身即大写入）

### 车载总线对比与 CAN 位定时/采样点

**一句话要点**：总线选型看成本与确定性：CAN 差分双线、显性 0/隐性 1、CSMA-CR 逐位仲裁，可靠性高成本低；CAN FD 数据 64 字节、数据段变速率；LIN 单线主从、低成本低速；FlexRay 时间触发（TDMA）、确定性最强；车载以太网高带宽、支撑 SOME/IP 与 OTA。CAN 接收端靠采样点判定位边界：位时间 = 同步段 + 传播段 + 相位缓冲段 1 + 2，采样点落在 PS1/PS2 之间，帧起始沿做硬同步、帧内沿做重同步补偿时钟偏差。
**面试怎么问**：CAN 与 LIN 各适合什么场景，怎么选型？采样点一般设多少、设不好会怎样？FlexRay 相比 CAN 的核心优势是什么？
**用例 / 示例**：
```text
总线对比表：
  总线       | 介质/拓扑          | 仲裁/调度         | 典型速率         | 定位
  CAN        | 差分双线, 多主总线  | CSMA-CR 逐位仲裁  | ≤1 Mbps         | 控制与诊断基石, 成本低可靠性高
  CAN FD     | 差分双线, 多主总线  | CSMA-CR           | 仲裁≤1M 数据≤8M | 大数据段, 兼容经典 CAN
  LIN        | 单线+地, 单主多从   | 主节点调度表      | ≤20 kbps        | 车身低速执行器(车窗/灯光/座椅)
  FlexRay    | 双通道差分, 总线/星型 | 时间触发 TDMA   | 10 Mbps/通道    | 确定性+容错, 线控/底盘安全域
  车载以太网  | 单对双绞线, 交换式   | 交换/点对点       | 100M~1Gbps      | 高带宽, SOME/IP/DoIP/OTA/影音

CAN 位时间与采样点（接收端判定位边界的依据）：
  位时间 = 同步段(1Tq) + 传播段 + 相位缓冲段1 + 相位缓冲段2
  采样点位于 PS1 与 PS2 之间, 典型配置 16Tq、采样点 87.5% (1+3+10)/16
  硬同步: 总线空闲→忙的下降沿(SOF)对齐, 只在帧起始发生
  重同步: 帧内每个显性→隐性跳变沿触发, 按偏差增减 PS1/PS2, 补偿节点晶振漂移
  采样点太早/太晚 → 长线缆+大传播延时下采到错误电平, 出现偶发 CRC 错误
```
**关联项目**：通用基础（总线选型）、预见性巡航（CAN 参数整定）

### CAN 高负载下低优先级帧饿死（场景题）

**一句话要点**：总线负载过高（>70~80%）时低优先级帧持续败仲裁会被"饿死"，CAN 本身无法靠软件抢总线，只能从设计端解决：按安全关键性分配 ID、调整发送周期与触发方式（事件触发/降频）、必要时网关分段或换 CAN FD 合并帧。
**面试怎么问**：总线负载 90% 时你负责的低优先级报文发不出去，怎么排查和解决？事件触发和周期发送怎么权衡？怎么评估总线负载率？
**用例 / 示例**：
```text
排查与对策思路：
  1. 先量化：用 CAN 分析仪统计负载率, 确认是否 >70~80%
  2. 优先级审查: 按安全关键性分配 ID —— 制动/转向类最小 ID, 车身/娱乐类让位
  3. 周期策略:
     - 低优先帧拉长周期(100ms→200ms), 先保证发得出
     - 状态变化/超阈值才发的"事件触发", 平时不占总线
     - 周期保底 + 事件即时上报的混合模式
  4. 动态降级: 高负载时暂停诊断/统计类非关键报文, 恢复后再发
  5. 结构性方案: 网关按域分段(动力/车身分总线), 或 CAN FD 合并多个小帧

负载率估算: 负载率 ≈ Σ(每帧占用时间 × 发送频率) / 1s
  例: 500kbps, 8 字节数据帧约 130 bit(含填充), 耗时约 0.26ms
      → 1ms 周期 4 个这样的帧就接近满负载, 必须做优先级与周期规划
```
**关联项目**：预见性巡航（ADAS 信号优先级规划）、主动安全系统、通用基础

### CAN 跨字节信号拼接与多帧一致性（场景题）

**一句话要点**：跨字节信号解析推荐手动"移位+掩码"（可移植、无对齐/端序坑），如 ((uint16_t)data[0]<<8)|data[1]；位域结构体虽简洁，但受编译器对齐、位序与大小端影响，车规代码基本不用。多帧组合信号（如 64 位拆两帧）要保证一致性：双缓冲/快照 + 时间戳对齐 + DLC 与更新位校验。
**面试怎么问**：车规代码为什么普遍不用位域解析 CAN 信号？有符号的跨字节信号怎么处理符号位？64 位信号拆两帧，中间丢一帧会怎样？
**用例 / 示例**：
```text
位域方案的问题（不推荐用于报文解析）：
  ① 编译器对位域分配顺序未完全统一, 依赖 ABI, 跨编译器结果可能不同
  ② 大小端平台位序不同, 同一结构体解析结果不一致
  ③ 位域不能取地址, 无法直接按 CAN 缓冲区解读, 且对齐靠 packed 扩展
  ④ 结论: 简洁但不可移植, 仅限单机内部、明确 ABI 的场合

推荐做法: 手动移位+掩码, 位序规则(Intel LSB/Motorola MSB)写死在解析函数
```
```c
#include <stdint.h>

/* 无符号 2 字节信号, 小端位序(低字节在前) */
uint16_t parse_u16(const uint8_t *data)
{
    return (uint16_t)(data[0] | ((uint16_t)data[1] << 8));
}

/* 有符号 2 字节信号: 先拼无符号, 直接转 int16_t 即完成符号扩展(补码) */
int16_t parse_i16(const uint8_t *data)
{
    uint16_t raw = (uint16_t)(data[0] | ((uint16_t)data[1] << 8));
    return (int16_t)raw;   /* bit15=1 时自动为负, 无需手工补 1 */
}

/* 多帧组合信号一致性: 64 位里程拆两帧(帧A=高32位, 帧B=低32位) */
typedef struct {
    uint32_t ts_ms;   /* 接收时间戳 */
    uint8_t  valid;   /* 两帧齐且 DLC 正确 */
    uint64_t value;   /* 组合值 */
} snap_t;

static snap_t snap[2]; /* 双缓冲: 生产者写 cur, 消费者读 !cur, 保证读到一致快照 */
static uint8_t cur;

void on_high_frame(const uint8_t *d, uint8_t dlc)  /* 帧A: 高32位 */
{
    if (dlc < 4) return;                 /* DLC 校验 */
    snap[cur].value = ((uint64_t)d[0] << 24) | ((uint64_t)d[1] << 16)
                    | ((uint64_t)d[2] << 8)  |  (uint64_t)d[3];
    snap[cur].ts_ms = now_ms();          /* 记录时间戳, 供消费端对齐 */
}

void on_low_frame(const uint8_t *d, uint8_t dlc)   /* 帧B: 低32位 */
{
    if (dlc < 4) return;
    snap[cur].value |= (uint64_t)d[0] | ((uint64_t)d[1] << 8)
                     | ((uint64_t)d[2] << 16) | ((uint64_t)d[3] << 24);
    snap[cur].valid = 1;
    cur ^= 1;                            /* 切换缓冲, 消费端读 !cur 必为完整快照 */
}

/* 消费端: 取 !cur 的快照; 若两帧间隔超阈值(如100ms)或 valid=0, 判为信号失效 */
```
**关联项目**：预见性巡航（ADAS 信号解析）、主动安全系统（信号一致性校验）、通用基础

### 车载场景 TCP vs UDP 选型与 SOME/IP 服务发现

**一句话要点**：选型口诀——实时流（音视频/环视/传感器高频流）用 UDP，容忍丢包但拒绝延迟；控制指令与诊断/刷写用 TCP，可靠有序优先。SOME/IP 服务发现（SD）让客户端知道服务端"提供什么"：服务端 Offer Service 广播上线、客户端 Find Service 主动查找、再 Subscribe Eventgroup 订阅事件，全程走 UDP 30490。
**面试怎么问**：车载音视频为什么用 UDP 而控制指令用 TCP？客户端怎么知道服务端有哪些方法可调？SOME/IP 相比裸 socket 通信的优势？
**用例 / 示例**：
```text
TCP vs UDP 车载选型：
  场景          | 协议 | 理由
  音视频流/环视  | UDP  | 实时性优先, 丢一两帧可容忍, TCP 重传反而卡顿
  传感器高频流   | UDP  | 数据量大、允许丢点, 配时间戳按帧对齐
  控制指令       | TCP  | 必须可靠有序, 丢一条指令可能造成误动作
  诊断/OTA 刷写  | TCP  | 大文件可靠传输+流量控制; DoIP 诊断消息走 TCP 13400

SOME/IP 服务发现(SD, UDP 30490)：
  1. Offer Service     服务端上线/周期广播: 我提供 ServiceID X, 含哪些方法/事件组
  2. Find Service      客户端广播查找: 谁提供 ServiceID X? (未收到 Offer 时主动找)
  3. Subscribe Eventgroup  客户端订阅事件组, 服务端回 Subscribe ACK
  4. 之后客户端即可 REQUEST/RESPONSE 调方法, 或收 NOTIFICATION 事件

相比裸 socket 的优势：
  ① 服务动态发现/动态上线: ECU 重启、新服务加入无需客户端硬编码地址
  ② 接口抽象: 方法/事件/字段语义化, 面向服务(SOA)跨域复用
  ③ 自带序列化、Length 前缀与返回码, 解析健壮、错误处理统一
  ④ 兼容 AUTOSAR 与 OEM 工具链, 适合整车级演进
```
**关联项目**：通用基础（SOA 演进方向）、OTA 排查支持（下载链路 TCP/断点续传）
