## ① 预见性巡航 PCC（第一重点）

> 复习指引：这是简历的"头号项目"，一面必讲，先背熟 1 分钟话术再按 STAR 展开，全程先讲结论和数据、再讲过程。
> 重要度：★★★★★
> 复习重点：WebSocket 长连接/心跳/重连、CAN 协议封装下发、151MB 内存优化、超时降级策略四个方向，每个都要能讲到具体做法和数据。

### 项目一句话

基于地图数据（百度/四维图新）感知前方道路信息，经 CAN 下发 CCU，优化动力控制实现节能。

### 项目 STAR

**背景**：宇通客车要降能耗。传统巡航不感知前方路况，坡道、弯道、限速无法提前响应，油耗电耗偏高。

**我的职责**：车端主力/主导，负责 PCC 完整数据链路：接收地图数据 → 解析 → 协议转换 → CAN 下发 CCU。

- 百度方案：WebSocket 长连接与云端双向通信，固定频率上报车辆位置（经纬度/航向/速度）；接收坡度、曲率、道路类型、限速，按 ADAS v2 CAN 协议封装周期报文下发 CCU
- 四维图新方案：HTTP 与云控平台对接，获取 SLOPE/STUB/POSITION 报文（坡度、路段桩号、位置），数据对齐与滤波后转发，支持云端 HP 功能
- 可靠性：数据超时判定、丢帧补偿、断线重连（指数退避），云端数据缺失时降级回普通巡航
- 性能：151MB 内存约束下监控 VmRSS/VmData 定位峰值，优化缓冲池与线程模型，避免 OOM、控制 CPU 占用

**技术亮点**：

- 百度 + 四维图新双地图方案并存接入（WebSocket / HTTP 两种通道）
- 151MB 资源受限环境下的内存与 CPU 优化（VmRSS/VmData 监控、缓冲池复用、减少拷贝）
- 超时判定 + 降级策略，保证地图数据缺失时仍安全行车

**结果**：随宇通批量车型上线，稳定运行【待补充：节油率/转发时延/稳定运行天数】

### 必考知识点（点击直达对应页面）

- [WebSocket：握手、帧格式、心跳、断线重连](#/04-net?goto=WebSocket：握手、帧格式、心跳、断线重连)——WebSocket 通过 HTTP Upgrade 完成握手后建立全双工长连接，数据以帧传输，应用层要自己实现 PING/PONG 心跳和断线重连；`面试怎么挂钩`：百度地图方案正是靠 WebSocket 固定频率上报位置、接收地图数据，心跳 + 指数退避重连是必问点。
- [HTTP/HTTPS 与 TLS 握手简述](#/04-net?goto=HTTP/HTTPS 与 TLS 握手简述)——HTTP 是无状态的明文请求/响应协议，HTTPS 在 TCP 之上加 TLS 加密层，握手协商套件、校验证书、非对称换密钥后转对称加密；`面试怎么挂钩`：四维图新方案走 HTTP 与云控平台对接，用这组对比讲两套地图通道的差异。
- [长连接 vs 短连接](#/04-net?goto=长连接 vs 短连接)——长连接一次建立多次传输，省去频繁握手开销，适合高频率小数据量通信；短连接每次新建用完即关，握手开销大；`面试怎么挂钩`：PCC 固定频率上报位置，所以选 WebSocket 长连接而非 HTTP 短连接，"为什么不用轮询"就用这组对比回答。
- [CAN 帧结构与报文解析](#/05-auto?goto=CAN 帧结构与报文解析)——标准帧 11 位 ID、扩展帧 29 位 ID，仲裁靠 ID + RTR 逐位比较、ID 越小优先级越高，位填充用于接收同步与错误检测；`面试怎么挂钩`：地图数据按 ADAS v2 协议封装成周期 CAN 报文下发 CCU，报文解析是基本功。
- [CAN 跨字节信号拼接与多帧一致性（场景题）](#/05-auto?goto=CAN 跨字节信号拼接与多帧一致性（场景题）)——跨字节信号解析推荐手动"移位+掩码"、车规代码基本不用位域；多帧组合信号要双缓冲/快照 + 时间戳对齐保证一致性；`面试怎么挂钩`：坡度、曲率等信号跨字节拼接解析，避免错位，也与 151MB 下的减少拷贝优化呼应。
- [生产者-消费者问题（手写伪代码）](#/03-os?goto=生产者-消费者问题（手写伪代码）)——用"互斥锁 + 两个条件变量"实现有界缓冲，满等 not_full、空等 not_empty，条件判断必须用 while 防虚假唤醒；`面试怎么挂钩`：地图数据接收线程与决策线程之间用环形缓冲解耦，数据到达过快时单独实现丢最旧帧策略。
- [环形缓冲区（加锁版与无锁版思路）](#/02-c?goto=环形缓冲区（加锁版与无锁版思路）)——环形缓冲区用 head/tail 指针 + 模运算实现 FIFO，留一个空位区分空/满，SPSC 场景可无锁（先写数据再更新指针 + 内存屏障）；`面试怎么挂钩`：地图数据与 CAN 下发之间的缓冲，面试官让手写时判空判满要脱口而出。
- [位操作（置位/清位/翻转/统计 1 的个数）](#/02-c?goto=位操作（置位/清位/翻转/统计 1 的个数）)——| 置位、&~ 清位、^ 翻转、& 判断，统计 1 的个数用 Kernighan 算法 x &= (x-1)；`面试怎么挂钩`：CAN 报文状态位、标志位处理与协议转换都离不开位操作。
- [内存四区与 malloc/free 原理（含内存碎片）](#/13-memory?goto=内存四区与 malloc/free 原理（含内存碎片）)——程序内存分栈、堆、全局/静态区（.data/.bss）、代码区（.text），malloc 底层走 brk/mmap，free 的内存进空闲链表复用而非立刻归还系统；`面试怎么挂钩`：151MB 约束下监控 VmRSS/VmData，先搞清每个区占了多少才能谈优化。
- [嵌入式为什么不推荐频繁动态内存](#/13-memory?goto=嵌入式为什么不推荐频繁动态内存)——嵌入式 RAM 小，堆碎片化后大块分配失败、分配耗时不可控、长期运行泄漏累积不可恢复，策略是启动时静态分配 + 固定内存池；`面试怎么挂钩`：PCC 的 151MB 优化正是用缓冲池复用代替频繁 malloc，避免 OOM。

### 面试追问 Q&A

- **Q：** WebSocket 断线怎么处理？
- **A：** 心跳保活 + 指数退避重连；重连成功后重新上报位置做状态同步；云端数据持续缺失时，超时判定后降级回普通巡航，保证安全。
- **Q：** 两套地图方案为什么并存？差异在哪？
- **A：** 供应商策略不同：百度走 WebSocket 长连接实时交互，四维图新走 HTTP 与云控平台对接；差异主要在数据精度、覆盖范围、协议形式【按实际补充具体对比】。
- **Q：** CAN 报文周期多少？数据怎么防抖/滤波？
- **A：** 【按实际回答具体周期数值，如 50ms/100ms】；对坡度、曲率等做数据对齐和滤波后再封装下发，避免抖动值直接进 CAN。
- **Q：** 151MB 内存怎么优化？
- **A：** 监控 VmRSS/VmData 定位内存峰值 → 缓冲池复用减少频繁申请 → 减少数据拷贝 → 控制线程数量，避免 OOM。
- **Q：** 地图数据长时间缺失怎么办？
- **A：** 超时判定 + 降级策略，退回普通巡航，保证行车安全。
- **Q：** 断线重连的退避参数怎么定？
- **A：** 指数退避（如 1s→2s→4s…封顶 60s，可按实际调整），避免重连风暴；重连成功后先拉取地图全量数据，补齐断线期间的路况。
- **Q：** 怎么验证功能正确？
- **A：** 台架联调 + 实车路测，与 CCU 联调日志核对报文下发是否符合 ADAS v2 协议【待补充：台架/路测里程数】。
