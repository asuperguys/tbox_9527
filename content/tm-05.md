# 05 · 协议层详解(补全理解,展示网络/协议能力)

> 本模块不是你的真实产出,但协议层是**嵌入式+车联网岗位面试的核心**。
> 讲好"JT808协议、TCP长连接、重传补传"能直接展示你的网络编程功底。
> 对应代码:`mdlSafety/ti_safety_protocol/` 与 `mdlSafety/subiao_safety_protocol/`

## 一、协议层职责总览

**设备 ↔ 平台**的全部通信都在这层:

| 功能 | 说明 |
|---|---|
| TCP长连接 | 连接天迈主动安全平台(主备IP切换、断线重连) |
| JT808协议编解码 | 组包/解包/转义(复用libSrc/jtt808_parser) |
| 注册/鉴权/心跳 | 上线三件套 |
| 定位上报 | 周期上报GPS |
| 报警上报 | 0x0201安全报警上传(核心!) |
| 参数设置/查询 | 0x8504/0x8505 |
| 透传 | 0x0900下行透传(ADAS/DMS注册、参数批量下发0x4005) |
| **重传机制** | ReSend808Controller:应答超时重发 |
| **补传机制** | HistoryDataMng:网络恢复后补发重要数据 |

**协议栈**:天迈主动安全协议 = JT/T 808(2019版)变种。
可选苏标(SAFETY_PTO_808JSU):江苏主动安全标准,报警事件定义不同。

## 二、JT808协议基础(面试必讲)

### 消息帧格式

```
┌──────┬───────────────┬──────────┬──────────┬──────┐
│ 0x7E │ 消息头(12~17B) │ 消息体    │ 校验码    │ 0x7E │
│ 起始 │               │          │ BCC      │ 结束 │
└──────┴───────────────┴──────────┴──────────┴──────┘
```

### 消息头(JT808HeadInfo)

```
消息ID(2B) | 消息体属性(2B:长度10位+加密3位+分包1位+版本1位) |
终端手机号(6~10B) | 消息流水号(2B,自增)
```

### 转义规则(面试常考)

```
0x7E ↔ 0x7D 0x02
0x7D ↔ 0x7D 0x01
发送时转义,接收时逆转义(jtt808_parser的Escape/Unescape)
```

### 2011版 vs 2019版(面试可加分)

| 差异 | 2011版 | 2019版 |
|---|---|---|
| 手机号 | 6字节 | 10字节 |
| 版本号 | 无 | 消息头加1字节协议版本 |
| 加密 | 3位加密方式 | 相同 |

> 天迈用2019版(`Ti_JTT808_PROTO::ParserMsgHead`),激活平台也用2019版。

## 三、TiProtocolManager 核心设计(面试重点)

### 3.1 命令字注册表 + 回调绑定(设计亮点!)

```cpp
// 命令字 → 处理函数列表(一个命令字可挂多个回调)
map<int, vector<ProtocolCmdFuncCallBack>> m_cmdFuncMap;
typedef std::function<int(PlatformAck_t&, void*)> ProtocolCmdFuncCallBack;

// 构造函数注册7个下行命令字:
RegProtocolCmdFunc(0x8100, 绑定ProtocolCmd_RegsterAck);        // 注册应答
RegProtocolCmdFunc(0x8001, 绑定ProtocolCmd_PlatformAck);       // 平台通用应答
RegProtocolCmdFunc(0x8504, 绑定ProtocolCmd_setPara);           // 参数设置
RegProtocolCmdFunc(0x8505, 绑定ProtocolCmd_queryPara);         // 参数查询
RegProtocolCmdFunc(0x8201, 绑定ProtocolCmd_alarmResponseProcess); // 报警应答
RegProtocolCmdFunc(0x8205, 绑定ProtocolCmd_PlatformCtr);       // 后台控制
RegProtocolCmdFunc(0x8900, 绑定ProtocolCmd_DevAdasOrDmsRegister_Ack); // 透传应答
```

> 面试话术:"协议层我用命令字注册表+回调绑定的方式做消息分发,收包后按命令字查表调对应处理函数,新增命令字就是注册一行,跟参数层的注册表设计一脉相承。"

### 3.2 三层回调桥接(理解JT808引擎如何接入)

```
Ti_JTT808_PROTO(PackMsg/ParserRawData)
  ├─ E_JT808_SEND_MSG        → DealSendSvrPacket → ProtocolProc_SendPacket(发送+重传入队)
  ├─ E_JT808_PARSER_MSGBODY  → DealRecvSvrPacket → ProtocolProc_DealSvrPacket(分发+重传删除)
  └─ E_JT808_ADD_HISTORY_MNG → DealTmpHistoryData → ProtocolFunc_TmpHistoryDataAdd(补传缓存)
```

> JT808解析库只管"帧解析/组包/转义",业务处理通过注册回调接入——**框架与业务分离**。

### 3.3 两个主循环

```cpp
// 收包线程:阻塞select循环
ProtocolMng_DataProc():
  select超时2秒 → 收包 → m_jtt808.ParserRawData()
  断线重连失败 sleep(5),收包异常 sleep(30)

// 秒级定时任务(外部线程每1秒调一次)
ProtocolProc_SecTask():
  ProtocolFunc_RegAuthMng()  // 注册/鉴权状态机
  按周期发定位包(posReportval)
  每180秒补传缓存写盘
  按周期发心跳(heartTimes)
```

## 四、注册/鉴权/心跳(上线三件套,面试必讲)

### 状态机(ProtocolFunc_RegAuthMng,每秒进入)

```
GB_UN_REG(未注册)
  ├─ 60秒连不上 → 切换主备IP
  └─ 连接成功 → GB_NEED_REG
GB_NEED_REG
  ├─ 有鉴权码 → 走鉴权(0x0102)
  └─ 无鉴权码 → 发注册(0x0100) → GB_REGING
GB_REGING(已发未答)
  └─ 30秒无应答 → 重发注册
GB_REGED(注册成功)
  └─ 发鉴权包 → 回到GB_REGING
```

### 注册包内容(SafetyDevReg_t,内容丰富)

国家/城市/公司/子公司/路队 + 主备服务器IP端口 + 终端型号 + 终端ID(7字节BCD) + 车牌号(UTF8→GBK) + 车辆编号 + 多媒体服务器 + DVR/BSD报警参数版本号 + 报警域名...

### 鉴权流程

```
发0x0102(带鉴权码) → 平台回0x8001通用应答
  → result==0且应答ID==0x0102 → 置m_anthSate=true(鉴权成功)
  → 触发ADAS/DMS透传注册(0x4008)
```

> 注意:鉴权码不落库,每次上电重新注册获取。

### 心跳流程

```
ProtocolCmd_Heartbeat: 发0x0002(空包体)
HeartBeatProcess: 上一周期未收到心跳应答,连续4次 → 强制断线重连
```

## 五、报警上传(0x0201)— 协议层核心!(面试重点)

### 报文结构(AlarmEventUploadInfo_t,固定头89字节)

```
length(2B)=89 | recordVer(1B)=0x01 | recordFlag(1B) 正常=0x01补采=0x02 |
alarmSn(4B)报警流水号 | terminalId(7B)终端ID | line(4B)线路 | busnum(4B)车辆编号 |
platenum(16B)车牌 | driveNum(32B)司机工号 | mileage(4B)里程 |
latitude(4B) | longitude(4B) | height(2B)海拔 | speed(2B)车速×10 |
direction(2B)方向 | recordLen(2B)子事件长度 | recordData[N]子事件数据
```

### 子事件类型(1字节命令字)

| 子命令字 | 含义 | 数据结构 |
|---|---|---|
| 0x63 | BSD系统报警 | BSDAlarmEventInfo_t |
| 0x64 | ADAS报警 | ADASAlarmEventInfo_t(碰撞时间/距离/偏离类型) |
| 0x65 | DMS报警 | DSMAlarmEventInfo_t(疲劳程度) |
| 0x66 | 三急报警(车辆) | CarAlarmEventInfo_t |
| 0x67 | ADAS/DMS连接状态 | - |
| 0x69 | 倒车雷达结果 | ReverseRadarEventInfo_t |

### 上报动作(双通道!)

```cpp
ProtocolCmd_AlarmEventUpload(sn, data, len):
  1. 组包(89字节头 + recordLen + 子事件数据)
  2. m_jtt808.PackMsg(ACTION_SEND_MSG)         // 实时上报
  3. m_jtt808.PackMsg(ACTION_ADD_HISTORY_MNG)  // 同时存补传匹配缓存
```

> 面试话术:"报警上传做了双保险——实时上报的同时把报文副本存进补传缓存,如果平台没收到,后续会通过补传机制补发,保证报警不丢。"

### 报警应答(0x8201)

```
平台回0x8201(应答流水号/报警流水号/报警ID/事件类型/结果)
  → resp_result==0 → 从重传队列删除该报警
```

## 六、重传机制(ReSend808Controller)— 设计亮点!

### 为什么需要重传

网络丢包时,普通TCP发送不保证业务层"送达确认"。定位/报警是重要数据,必须有**业务层确认机制**。

### 设计

```cpp
// 注册参与重传的命令字 + 对应应答命令字
ProtocolReSend_RegEffectiveCmd(0x0200定位, 0x8001平台通用应答);
ProtocolReSend_RegEffectiveCmd(0x0201报警, 0x8201报警应答);

// 发送时入队(ProtocolProc_SendPacket)
m_resendCtl->addReSendTask(len, buf, sn, cmd, sendMax=5);
// 定位包特殊:sendMax=1(只发一次,靠补传兜底)

// 收到应答时出队(ProtocolProc_DealSvrPacket)
// 0x8001通用应答:按(应答的上行命令字, 流水号)删除
// 0x8201报警应答:按报警流水号删除
// 专用应答:命令字&0x0FFF还原上行命令字删除

// 独立重传线程:周期扫描hash表,超时未应答的重发,直到sendMax
```

### 重传失败 → 补传(接力!)

```cpp
ProtocolFunc_failResendNext(cmd, sn, ...):
  // 重传耗尽 → 从匹配缓存转移到补传数据队列
  m_historyDataMng->mvItemFromMatchCacheToDataCache(cmd, sn);
```

## 七、补传机制(HistoryDataMng)— 面试亮点!

### 为什么要补传

重传是"短期重试"(秒级),如果网络长时间中断,重传耗尽后数据会丢。补传把数据**持久化到文件**,网络恢复后补发。

### 两级存储 + 磁盘文件

```
内存缓存m_dataCache(待补传队列)
  ↕ 180秒写盘 / 启动读盘
磁盘文件HISTORY_DATA_FILE(/mnt/nand/safety_history_data,文本格式每行一条hex)
匹配缓存m_matchCache(≤50条,循环覆盖)
```

### 数据流

```
实时上报 ──ACTION_ADD_HISTORY_MNG──▶ 匹配缓存
                                        │
重传失败 ──failResendNext──▶ 转入补传数据队列
                                        │
定位包应答成功(通信恢复)──▶ 触发补传消费:
                             加载文件→循环popItemFromDataCache→逐条补发
                                        │
                             每180秒缓存写盘(防掉电丢失)
```

### 触发时机(设计巧妙)

> **收到定位包的通用应答** = 通信环境恢复正常 = 开始补传。用"定位包应答"做网络恢复探针,天然与心跳节奏耦合。

### 防重入

`HISTORY_STATUS_IDLE/BUSY` 状态:补传执行中置BUSY,防止秒级任务重复触发。

## 九、苏标协议(subiao_safety_protocol)— 了解即可

### 与天迈协议的差异

| 维度 | 天迈 | 苏标 |
|---|---|---|
| 平台连接 | AI直连平台TCP | 通过调度主链接透传 |
| 报警上报 | 0x0201直接上报 | 事件打包后交调度上传 |
| 附件 | HTTP上传 | 0x9208指令 → TCP附件服务器(0x1210~0x1212) |
| DMS事件 | TM_DMS_EVENT_* | JSuDMS_EVENT_*(疲劳=0x01,接打电话=0x02...) |

### 苏标附件上传流程(0x9208)

```

  → jiangSuAppendixItem_st 入队
  → SuBiaoAdx_BlockedUploadTask线程处理:
      CHECK_SVR_ALARMNUM → 查平台报警编号
      → 连附件服务器 → 上传文件信息(0x1210) → 传文件数据(0x1211) → 完成(0x1212)
```

## 十、协议层已知问题(优化素材)

| 问题 | 说明 |
|---|---|
| 报警子事件校验恒为假 | `(0x63>data[0]) && (data[0]>0x69)` 永不成立,非法ID不拦截 |
| data[0]空指针解引用 | data==NULL时仍访问data[0]打日志,会崩溃 |
| 海拔被方向覆盖 | 0x0201组包height被direction值覆盖 |
| 全参数查询0x8505未发送 | getAllPara组包后PackMsg被注释 |
| 自检内存泄漏 | new SafetyDevSelfTest_t从未delete |
| 抓拍应答恒失败 | result变量从未赋值 |
| 补传统一按定位命令字发 | 报警补传数据也发成定位包 |
| 鉴权码不落库 | 每次上电重新注册 |
| 无锁共享状态 | m_platformStatus等跨线程无锁 |

## 十一、面试问答准备(本模块)

**Q1:重传和补传有什么区别?**
> 重传是短期的:报文发出后加入重传队列,超时未收到平台应答就重发,最多5次。补传是长期的:重传失败后数据转入补传队列并持久化到文件,网络恢复后(以定位包应答为信号)统一补发。重传解决瞬时丢包,补传解决长时间断网,两者接力保证重要数据不丢。

**Q2:为什么用定位包应答做补传触发信号?**
> 定位包是周期性必发的报文,它的应答能代表"网络链路当前是否畅通"。收到定位应答说明平台可达,此时补传成功率最高。而且天然有节奏,不会在断网时反复尝试补传浪费资源。

**Q3:JT808转义是怎么回事?**
> 帧的起始和结束标志都是0x7E,如果报文内容里出现0x7E或0x7D会破坏帧边界,所以发送时0x7E转成0x7D 0x02,0x7D转成0x7D 0x01,接收时逆向还原。

**Q4:心跳怎么判断链路断开?**
> 发心跳后看是否收到通用应答,连续4个周期没应答就认为链路异常,主动断开重连。

**Q5:注册鉴权流程?**
> 连上服务器→发注册包(设备信息)→平台回注册应答带鉴权码→发鉴权包→平台通用应答确认→鉴权成功→开始心跳/定位/报警业务。鉴权成功后还会触发ADAS/DMS透传注册。

**Q6:如果让你优化协议层,你会改什么?**
> 一是修那几个确定的bug(校验恒为假、空指针、海拔覆盖);二是给共享状态加锁;三是补传按原命令字发送而不是统一按定位包;四是去掉遗留的HexPrint调试打印。

## 十二、核心记忆卡(背诵)

```
上线三件套:注册(0x0100)→鉴权(0x0102)→心跳(0x0002)
```
