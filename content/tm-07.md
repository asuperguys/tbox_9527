## 二、你的两个主战场:深入叙事剧本

### 故事A:三急报警(急加速/急减速/急转弯)

**背景(为什么做)**
> 主动安全除了视觉算法报警,还需要基于传感器数据的**驾驶行为报警**——急加速、急减速、急转弯,这是平台监管的"三急"事件。数据来源是车上的六轴传感器(ICM-20600:3轴加速度+3轴陀螺仪),通过调度子系统转发给AI。

**我负责什么**
> 六轴数据的解析、三急的判定算法、报警触发的完整链路(从传感器原始值到报警事件上报)。

**难点(面试核心,要讲透)**
1. **传感器数据不可靠**:
   - 陀螺仪有**温漂/零点漂移**,温度变化导致基准值偏移
   - 加速度计测的是**重力+运动加速度的合成值**,静止时也有读数
   - 车辆晃动会产生大量**干扰信号**,直接判定会误报
2. **安装方向不确定**:同一设备在不同车辆上安装朝向不同(车顶/车底、正装/侧装),导致需要读取的传感器轴不同
3. **阈值难定**:触发阈值是经验值,需要现场调试

**我的方案**
1. **温漂处理**:滑动窗口均值(最近10个值≈2秒数据)+ 抖动阈值过滤——低于阈值的波动视为干扰,用均值代替,滤掉温漂和晃动
2. **平衡值预测算法**:从合成加速度中分离真实加减速——静止时的读数作为基准(平衡值),运动时看与平衡值的偏差;偏差>阈值判定急加速(正波)或急减速(负波);连续稳定后重新采样平衡值,防止基准漂移
3. **安装方向自适应**:从数据库读取设备安装方向配置(LED朝向/顶壳朝向),自动确定要读取的传感器轴,换车不改代码
4. **三层过滤**:抖动阈值(0.3)→事件阈值(0.7)→上报间隔过滤(与上次触发时间差),最大限度防误报
5. **车速分级**:按实时车速分1/2/3级,执行不同的联动动作(语音/抓拍/视频等)

**收获**
> 学会了"传感器数据的信号处理思路"——真实场景的数据永远有噪声,算法不只是判定逻辑,更是噪声处理、基准估计、状态机的组合;也体会到嵌入式产品要面对**安装工艺差异**这种"非技术"问题,需要用配置化方案解决。

### 故事B:参数配置管理

**背景**
> 主动安全系统有几百个参数:设备基本参数(服务器地址/心跳间隔)、算法参数(摄像头通道/标定)、报警事件参数(每个子事件的开关/灵敏度/间隔/联动动作)。来源有三个:平台下发(0x8504)、安卓App设置(JSON)、本地默认值。

**我负责什么**
> 参数注册表的设计、平台参数下发链路的对接、安卓App的JSON交互、数据库存取、参数变更后与算法侧的联动。

**难点**
1. 参数数量大(几百个)、来源多(平台/App/默认值)、格式杂(字节/字符串/逗号分隔)
2. 协议命令字ID与数据库字段、内存结构之间需要稳定映射
3. App下发的是JSON,需要校验、映射、落库
4. 参数变更后需要通知算法侧重载,但不能频繁重载(重载会重启算法)

**我的方案**
1. **参数注册表设计**:每个参数ID一条注册记录(表名/字段/类型/默认值/解析函数/更新通知),新增参数=加一行注册,零侵入
2. **三层解耦**:协议命令字→注册表→数据库→内存结构,平台下发按ID查表全链路存取
3. **变更计数联动**:UI/App更新通知后重读库,比较"变更计数"判断参数是否真的变了,变了才触发算法重载(LoadDmsParaToAlg→AlgReInit)
4. **JSON交互**:解析App下发(模块枚举fr/dms/adas/bsd1-4)、参数范围校验、错误码返回;上传时组全部参数JSON;支持中英泰多语言
5. **ini内存文件**:算法运行状态(激活/帧率/报警计数)周期写入,UI跨进程读取,变化检测避免频繁IO

**收获**
> 学会了"配置驱动开发"的思想——用一张注册表管理所有参数,而不是每个参数写一堆if-else;也理解了嵌入式系统里**多进程间数据共享**(ini文件/域通信/SQLite)的不同手段和取舍。

### 故事C:CAN 信号级重构(面试大杀器,详见 [11 文档](#/tm-11))

**背景**
> 我负责的外部数据模块,原来的实现是"帧级解析打印"——每次收包整体解析赋值。我发现三个隐患:不同ID帧交错到达时字段互相误清;车速等状态型数据停止更新后业务仍拿旧值;高频数据下三急判定直接在收包线程跑会阻塞收包。

**我做了什么**
> 把模块重构为**信号级处理**:新增一个零依赖的 CAN 信号管理框架(信号注册表+信号槽+超时监控+变化检测+批量更新),解析只更新信号槽,业务按需读取并感知有效性;三急判定降频到100ms,日志降频到5s;配了独立单元测试,对外接口全部保持不变。

**难点与方案**
1. 字段互相误清 → 信号级独立存储,每帧只更新本帧包含的信号
2. 数据陈旧 → 500ms超时,读取时惰性判断 + 1s周期线程主动检查
3. 收包阻塞 → 业务降频(100ms节流),与收包解耦
4. 高频锁开销 → 批量更新单锁一次处理多信号
5. 回归风险 → 对外接口不变 + 独立单测 + 原文件备份

**与宇通项目的衔接(点睛)**
> 这套方法论直接迁移到我后来做的整车 CAN(每秒约1700帧):解析与业务解耦、攒批处理(10ms约17帧)、周期发布+version变化检测、信号超时有效性——本质是把 CAN 处理从"逐帧事件驱动"变成"信号状态管理",与 AUTOSAR COM 一致。

**收获**
> 学会从"数据流设计"角度审视嵌入式模块:高频场景下,解析/存储/消费三阶段解耦 + 信号级有效性管理是通用解法;也学会了用"接口不变+单测+备份"控制重构风险。

## 五、避免踩的坑(诚实原则)

1. **不要说自己做了算法抽象层/协议层**——那不是你的产出,但可以说"我深入理解/完整掌握"。
2. **不要说项目是完美的**——主动提出"我梳理时发现了一些问题"(见[09 文档](#/tm-09)),反而加分。
3. **不要说"都是我做的"**——团队项目,讲清分工和协作。
4. **不要背代码**——面试官会追问细节,讲思路和取舍,代码细节对照源码心里有数即可。
