# 22 · 整车 CAN 1700帧/s 数据链路设计方案(宇通场景,作品级)

> 这是你在宇通整车 CAN(每秒约1700帧)场景的**系统设计方案**,也是面试车联网/嵌入式岗位的"作品"。
> 与 [11 文档](#/tm-11)(信号级框架)一脉相承,但这里是**完整的数据链路工程方案**——从总线接收到业务消费。
> 面试讲法:"我在天迈做了信号级框架,后来在做整车 CAN 时把它扩展成了完整的数据链路方案。"

---

## 一、需求与挑战量化(先讲清楚问题)

### 1.1 量级感受
| 指标 | 数值 | 含义 |
|---|---|---|
| 帧率 | 1700 帧/s | 平均每 **0.59ms** 一帧 |
| 单帧处理预算 | < 0.5ms | 超过则积压/丢帧 |
| 单帧数据 | 8~64 字节 | CAN≤8,CAN-FD≤64 |
| 总数据量 | 约 30~100KB/s | 数据量不大,难在**每帧都要处理** |
| 总线 | 500kbps(动力CAN) | 利用率约 27%(8字节帧) |
| 报文种类 | 几十~上百种 ID | 周期性(10~100ms)+ 事件型 |

### 1.2 四个核心难点(面试必讲)
1. **处理次数多**:每秒 1700 次"收帧→解析→更新→可能唤醒业务"
2. **周期性 + 事件型混合**:周期报文要按信号更新,事件报文要即时响应
3. **数据陈旧不可用**:某个信号断更,消费端必须能感知
4. **抖动与突发**:总线错误重发、瞬时突发,不能阻塞主链路

---

## 二、总体架构(分层设计)

```
┌─────────────────────────────────────────────────────────┐
│ 应用层:整车功能(车速/能耗/诊断/安全...)                  │
├─────────────────────────────────────────────────────────┤
│ 信号消费层(周期发布):按 10ms 周期批量读变化信号            │
├─────────────────────────────────────────────────────────┤
│ 信号管理层 CanSignalMgr(注册表+信号槽+超时+version)      │
├─────────────────────────────────────────────────────────┤
│ 帧解析层(攒批):CAN帧 → 拆信号 → 批量写槽                 │
├─────────────────────────────────────────────────────────┤
│ 接收层:SocketCAN 原始帧 + 内核过滤 + 环形缓冲             │
└─────────────────────────────────────────────────────────┘
```

**核心思想**:把"逐帧事件驱动"变成"信号状态管理"——
- 接收层只收帧;解析层攒批拆信号写槽;业务按周期批量消费。三层解耦,互不阻塞。

## 三、各层设计细节

### 3.1 接收层(SocketCAN,内核过滤)

```c
// 1. 打开并绑定 CAN 接口
int s = socket(PF_CAN, SOCK_RAW, CAN_RAW);
struct sockaddr_can addr = { .can_family = AF_CAN, .can_ifindex = if_nametoindex("can0") };
bind(s, (struct sockaddr*)&addr, sizeof(addr));

// 2. 内核级 ID 过滤(只收关心报文,省用户态处理)
struct can_filter filter[] = { {.can_id = 0x100, .can_mask = 0x7FF},
                               {.can_id = 0x200, .can_mask = 0x7FF} };
setsockopt(s, SOL_CAN_RAW, CAN_RAW_FILTER, &filter, sizeof(filter));

// 3. 非阻塞 + 轮询/EPOLL 接收
fcntl(s, F_SETFL, O_NONBLOCK);
```

**要点**:内核过滤只收关心的 ID(如几十个),把 1700帧/s 之外的帧挡在内核;应用层只处理关心报文。

### 3.2 帧解析层(攒批处理)

```cpp
// 攒批:每 10ms 收一批(约17帧),批量处理,减少线程切换与锁竞争
void FrameRxThread() {
    struct can_frame frames[64];
    while (1) {
        int n = recvframes(s, frames, 64, 10ms_timeout);  // 攒10ms或64帧
        if (n <= 0) continue;
        ProcessBatch(frames, n, nowMs());                  // 批量解析
    }
}

void ProcessBatch(struct can_frame* frames, int n, uint32_t nowMs) {
    CanSignalMgr::CanSignalUpdateItem_t items[64];
    int cnt = 0;
    for (int i = 0; i < n; i++) {
        // 按帧ID查报文矩阵,拆成信号;关键信号(制动/转向)立即处理
        if (IS_CRITICAL(frames[i].can_id)) { HandleCritical(frames[i]); continue; }
        // 普通信号攒进批量
        ParseFrameSignals(frames[i], items, &cnt, 64);
    }
    mgr->updateBatch(items, cnt, nowMs);   // 单锁批量写槽
}
```

**攒批的好处**:① 处理次数从 1700次/s 降到 100次/s(10ms批)② 单锁批量,锁竞争降到 1/17 ③ 线程切换大幅减少。

### 3.3 信号管理层(复用 [11 文档](#/tm-11)框架)

```
CanSignalMgr:
  - 信号注册表:按 DBC 报文矩阵生成(ID→信号定义)
  - 信号槽:预分配数组,O(1)索引,零动态内存
  - 超时监控:周期信号超时自动置无效(按信号类型分级)
  - version 变化检测:消费端只处理变化信号
```

### 3.4 消费层(周期发布 + 变化检测)

```cpp
// 业务按 10ms 周期批量消费,不逐帧唤醒
void AppTick_10ms() {
    for (每个关心的信号) {
        uint32_t ver;
        mgr->getUpdateInfo(sigId, lastMs, ver);
        if (ver != lastSeenVer[sigId]) {       // 只处理变化的信号
            mgr->getWithTime(sigId, nowMs, &val);  // 带有效性
            if (有效) 更新业务状态;
        }
    }
}
```

## 四、性能预算(面试讲"算过账")

| 项目 | 预算 | 说明 |
|---|---|---|
| 单帧解析 | <10μs | 按ID查表+位提取,无动态内存 |
| 攒批处理 | 10ms批≈17帧,<200μs | 单锁批量 |
| 接收线程 CPU | <5% | 大部分时间阻塞等帧 |
| 信号槽内存 | 每信号~32B × 数百 = 十几KB | 预分配 |
| 锁 | 批量更新1次/10ms,临界区<1μs | 无竞争 |

> 面试话术:"我算过:1700帧/s 如果用逐帧处理,每秒 1700 次函数调用+锁;攒批后降到 100 次/秒,单帧解析微秒级,接收线程 CPU 占用可以控制在 5% 以内,给上层业务留足资源。"

## 五、可靠性设计(关键信号不丢不陈旧)

### 5.1 三级保障
| 级别 | 机制 | 适用 |
|---|---|---|
| 1 | 内核过滤 + 环形缓冲(突发吸收) | 所有报文 |
| 2 | 信号超时置无效(读时惰性+周期检查) | 状态型信号 |
| 3 | 关键信号(制动/转向/ACC)单独即时处理 + 事件队列 | 安全相关 |

### 5.2 关键信号优先
```cpp
// 关键信号(制动踏板/转向角/ESC状态)不攒批,收到即处理
// 用独立高优先级队列,确保安全信号延迟 <1ms
if (IS_CRITICAL(id)) {
    criticalQueue.push(frame);   // 由高优先级线程消费
} else {
    batchItems[cnt++] = ...;     // 普通信号攒批
}
```

### 5.3 丢帧/异常处理
- 接收计数统计(每秒校验应收 vs 实收)
- CRC 错误率监控(SocketCAN 内核已检)
- 超时信号置无效 → 业务降级(如车速无效用默认值)
- 环形缓冲溢出策略:丢旧保新(最新状态优先)

## 八、面试问答预案

**Q1:为什么攒批而不是逐帧?**
> 1700帧/s 逐帧处理 = 每秒1700次线程调度+锁+函数调用;攒10ms批(约17帧)降到100次/秒,锁竞争降1/17,线程切换大幅减少。实时性损失(10ms)对车载状态类信号完全可接受。

**Q2:事件型报文(如碰撞)也要攒批吗?**
> 不。事件型和安全关键信号走独立即时通道(高优先级队列),不攒批;攒批只针对周期性状态信号。两类分开处理。

**Q3:怎么证明不丢帧?**
> 接收端统计:每周期"应收帧数(按报文周期推算)" vs "实收帧数",偏差报警;CAN 帧本身有 CRC(内核检),应用层主要看计数和队列积压。

**Q4:1700帧/s 会不会把 CPU 打满?**
> 算过:攒批+内核过滤+O(1)索引后,接收与解析总开销 <5% CPU(单核),主要瓶颈不在 CPU 而在"别让业务跟着每帧跑"。解法就是信号状态管理——业务按周期批量读,不逐帧唤醒。

**Q5:和 AUTOSAR COM 的关系?**
> COM 是完整规范(PDU路由/信号组/超时/周期发送);我做的是应用层轻量实现,取核心思想,零依赖可移植,适合不依赖 AUTOSAR 栈的项目。方向一致,复杂度按需裁剪。

## 九、落地路线(宇通实际推进)

```
第1周:搭 SocketCAN 接收 + 计数验证(确认1700帧/s 与总线负载)
第2周:导入 DBC → 生成信号注册表 → 接入 CanSignalMgr
第3周:实现攒批解析 + 周期发布消费,单测+录波回放验证
第4周:关键信号优先队列 + 超时分级 + 联调整车功能
```

> 每阶段都有可验证的里程碑(帧计数/CPU占用/信号时延),这是嵌入式工程推进的标准方式——面试讲这个展示"规划落地"能力。
