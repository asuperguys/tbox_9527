### FOTA 与 SOTA 的区别

**一句话要点**：FOTA（Firmware OTA）升级固件/系统镜像，涉及分区写入与重启切换；SOTA（Software OTA）升级应用、服务、配置、内容等上层软件，不动系统底层。判断标准：是否涉及「分区/镜像级」写入——是就是 FOTA，只换上层文件就是 SOTA。

**面试怎么问**：FOTA 和 SOTA 的本质区别？T-Box 上哪些能 SOTA、哪些必须 FOTA？

**用例 / 示例**：
```text
T-Box 的升级对象分级：
  层级       | 例子                     | 升级方式
  系统镜像   | Linux 内核 / 根文件系统   | FOTA（整包/差分写分区）
  底层固件   | 基带/模组固件、MCU 固件   | FOTA（UDS 34/36/37 或模组私有协议）
  中间件     | 网络管理、OTA 客户端本身  | FOTA 或 SOTA
  应用服务   | 远程控制、数据上报、诊断   | SOTA（服务/进程包替换）
  配置数据   | APN、证书、业务配置       | SOTA（配置文件 + 版本号）
  内容       | 地图、离线语音包          | SOTA（大文件下载）
```
**关联项目**：OTA 排查支持（常见现象就是「某类升级失败」）

### 升级包类型：全量包 vs 差分包

**一句话要点**：全量包 = 新版本完整镜像/文件，简单可靠、不依赖源版本，缺点是流量大；差分包 = 新旧版本差异补丁，流量可缩小 80%+，但要求设备准确知道源版本（基线），基线不匹配会导致打补丁失败。

**面试怎么问**：什么时候用全量、什么时候用差分？差分失败怎么兜底？

**用例 / 示例**：
```text
选型权衡：
  全量包：首次升级、版本跨度大、无法确认基线、刷写可靠性优先 → 用全量
  差分包：频繁小版本迭代、流量/时间敏感（移动网络升级）→ 用差分
  混合策略：设备上报源版本 → 服务端匹配基线生成差分包
            → 基线匹配失败自动降级为全量包

典型数字：车机/车联网固件全量几十~几百 MB，差分常压到 10~30%。
```
**关联项目**：OTA 排查支持（差分包应用失败的常见根因：基线不符）

### 差分升级原理（bsdiff / 块级差分）

**一句话要点**：二进制差分核心思路——按块比较新旧文件：相同块记「引用旧文件」，变化块直接携带新数据，生成补丁；设备端用「旧文件 + 补丁」重建新文件。常用算法：bsdiff/bspatch（字节级、压缩率高）、块级哈希差分（分块 sha256 比较、实现简单抗错位）。

**面试怎么问**：差分补丁为什么必须知道旧版本？补丁应用一半断电会怎样？应用前后各校验什么？

**用例 / 示例**：
```c
/* 块级差分示意（块大小如 64KB）：
 * 服务端：对旧/新文件按块算 sha256 → 相同块标 REF，不同块标 DATA
 * 设备端：旧文件 + 补丁 → 重建新文件 → 全文件校验通过后原子替换 */
typedef struct {
    uint32_t block_idx;   /* 块序号 */
    uint8_t  type;        /* 0=引用旧块 1=携带新数据 */
    uint32_t new_len;     /* 新块长度 */
    uint8_t  sha[32];     /* 新块哈希（重建后校验） */
} patch_block_t;

/* 保护措施：应用补丁前先校验旧文件哈希（确认基线一致）；
 * 重建写入临时分区/文件，全部完成并校验通过后，再原子替换正式分区——
 * 避免补丁应用一半断电留下半新半旧的文件 */
```
**关联项目**：OTA 排查支持（差分失败 = 基线校验不通过是高频根因）

### A/B 双分区与无缝升级

**一句话要点**：设备划分两个相同的系统槽位（slot A / slot B，各含独立 boot 分区），当前从 A 启动，OTA 把新版本写入 B；写完标记 B 有效，重启后 bootloader 校验 B 通过则从 B 启动（A/B 互换），失败则回 A 继续用——升级过程完全不打断当前系统（seamless update），失败也不变砖。

**面试怎么问**：A/B 分区为什么能防变砖？切换槽位靠什么标志？两个槽位版本不一致怎么办？

**用例 / 示例**：
```text
A/B 启动流程：
  1. 当前运行 slot A（版本 v1）
  2. 后台下载 v2 包，写入 slot B（不影响 A 运行）
  3. 写入完成 → 置槽位标志：下次尝试 B
  4. 重启 → bootloader 校验 B（签名 + 哈希 + 版本）
  5. 校验通过 → 从 B 启动，成功后提交「已成功」标志
  6. 校验失败 / 连续启动失败 → 回退 slot A，业务零感知

槽位状态字段（存 misc 分区 / NVRAM）：
  unbootable / active / success / retry
  retry 计数：每次尝试 -1，归零即判失败并回滚
```
**关联项目**：OTA 排查支持（「升级后反复重启」= 槽位校验失败触发回滚的典型现象）

### 单分区升级与回滚兜底

**一句话要点**：存储紧张时用单分区：原地覆盖升级，省一半空间，但升级失败可能变砖，必须有兜底——保留旧版本备份区、bootloader 校验 + 看门狗式回滚、连续 N 次启动失败自动进 recovery。

**面试怎么问**：单分区升级到一半断电怎么办？为什么很多设备宁可多花空间用 A/B？

**用例 / 示例**：
```text
单分区 + 备份回滚方案：
  分区布局：bootloader | app(新) | backup(旧) | config | recovery

  升级前：旧版本已存在于 backup（或升级时先把旧版搬过去）
  升级中：写入 app，置 upgrade_flag = IN_PROGRESS
  启动时：bootloader 见 IN_PROGRESS → 校验 app
      校验通过 → 置 SUCCESS，正常启动
      校验失败/起不来 → 从 backup 恢复，置 ROLLBACK
  连续 N 次启动失败 → 进 recovery（可恢复出厂 / 重新升级）

空间对比：A/B 需 2 倍系统空间；单分区+备份 ≈ 1.5 倍；recovery 分区必留。
```
**关联项目**：GNSS 固件升级（UDS 刷写 + 升级标志位）、OTA 排查支持

### 签名与验签（防篡改）

**一句话要点**：升级包由 OEM 私钥签名（对包内容哈希做 RSA/ECC 签名），设备内置公钥验签：算包哈希 → 用公钥验证签名 → 通过才允许解析/刷写。公钥必须固化在安全区（eFuse/OTP/安全启动链），验签逻辑必须放 bootloader（比应用更底层，防绕过）。

**面试怎么问**：验签放 bootloader 里有什么好处？私钥泄露怎么处置？验签失败该不该继续刷写？

**用例 / 示例**：
```text
验签流程：
  1. 设备收到升级包 → 提取 [包数据 + 签名值]
  2. 对包数据计算哈希 H = SHA256(data)
  3. 用内置公钥验证签名 → 还原出包内声明哈希 H'
  4. 比对 H == H' 且签名者身份匹配 → 验签通过，进入解析/刷写
  5. 任一步失败 → 丢弃该包，上报验签失败，禁止写入

关键点：
  - 公钥只读固化（eFuse/OTP），应用层拿不到私钥
  - 签名算法：RSA-2048/4096 或 ECC P-256（更小更快，车规常用 ECC）
  - 验签失败必须停止刷写——这是防「假升级包/中间人替换」的最后防线
```
**关联项目**：OTA 排查支持（验签失败 = 包不完整 / 签名过期 / 密钥不匹配）

### 防回滚（anti-rollback）

**一句话要点**：攻击者可能拿含已知漏洞的旧版本固件重放降级，防回滚用「版本计数器」解决：每次成功升级把版本号写入一次性可写存储（RPMB / OTP / 安全计数器，只增不减），bootloader 校验新版本必须 ≥ 当前计数，否则拒绝启动/刷写。

**面试怎么问**：为什么既要防回滚又要能回滚？两者矛盾吗？版本号存哪才安全？

**用例 / 示例**：
```text
防回滚机制：
  - 升级包头带 version（如 0x0103）
  - 设备安全区存 rollback_counter（RPMB/OTP，只能增不能减）
  - bootloader：新版本 < 当前计数 → 拒绝启动/刷写（防降级攻击）
  - 升级成功后：rollback_counter = 新版本

防回滚 vs 业务回滚：不矛盾——
  「业务回滚」= 升级失败时切回旧版本继续用
  「防回滚」  = 禁止把版本降到安全阈值以下（堵已知漏洞）
  实际方案：允许回滚到「大于等于最低安全版本」的旧版，禁止低于下限。
```
**关联项目**：市场问题分析（版本管理相关故障）、OTA 排查支持

### 传输加密与包体加密

**一句话要点**：两道加密各司其职——传输层用 HTTPS/TLS 防窃听篡改（云端↔设备链路安全）；包体用 AES（密钥放 HSM/安全区）防静态逆向（包被拷走也读不出内容）。签名负责「防篡改 + 来源认证」，加密负责「防泄露」，面试要分开讲清。

**面试怎么问**：签名和加密的区别？设备密钥放哪？为什么包体要加密？

**用例 / 示例**：
```text
安全分层：
  层级       | 手段                          | 防什么
  传输层     | HTTPS/TLS + 证书双向认证       | 中间人窃听/篡改下载内容
  包体层     | AES 加密（设备密钥/会话密钥）  | 包被拷走也读不出固件
  内容层     | 签名（RSA/ECC）               | 伪造/篡改升级包
  版本层     | 版本计数器（RPMB/OTP）        | 降级重放攻击
  设备层     | Secure Boot + HSM             | 启动链被注入/密钥被提取

典型链路：TLS 下载密文包 → 设备 HSM 解密 → 验签 → 校验哈希 → 写入分区
```
**关联项目**：eSIM（LPA 与 SM-DP+ 证书双向认证同思路）、OTA 排查支持

### 云端链路与灰度发布

**一句话要点**：升级由云端编排：创建任务（车型/VIN 范围/版本）→ 灰度分批下发 → 设备查询/推送获取任务 → 下载 → 校验 → 刷写 → 上报结果；灰度按比例/批次放量，出问题立即暂停，避免全网事故。

**面试怎么问**：灰度发布是什么、怎么设计？设备怎么知道自己有升级任务？

**用例 / 示例**：
```text
云端 → 设备链路：
  云平台（任务管理 / 包管理 / 统计）
    → 按策略下发（VIN 清单 / 灰度比例 1%→10%→100%）
    → 设备端 OTA 客户端 轮询/长连接 获取任务
    → 下载（HTTPS + 断点续传）→ 校验 → 刷写 → 上报状态
    → 云平台统计成功率，异常批次暂停/回滚

灰度设计要点：
  - 先内部车辆（研发/测试）→ 小比例白名单 → 逐级放量
  - 每级观察 24~48h：升级成功率、回滚率、失败 NRC 分布
  - 超阈值自动暂停（熔断），人工确认后再放量
```
**关联项目**：OTA 排查支持（现场排查常先看「任务批次是否被暂停/回滚」）

### 设备端状态机与断点续传

**一句话要点**：设备端 OTA 是严格状态机：IDLE → TASK_RECEIVED → DOWNLOADING → VERIFYING → INSTALLING → SUCCESS / FAILED / ROLLBACK；每一步的状态、偏移量、校验值都要持久化（NVRAM/文件），崩溃重启后从断点恢复，避免从头再来。

**面试怎么问**：升级一半断电重启，怎么做到不从头再来？状态文件写坏了怎么办？

**用例 / 示例**：
```c
typedef struct {
    uint32_t magic;        /* 魔数，防误读 */
    uint8_t  phase;        /* 0=IDLE 1=下载中 2=校验中 3=刷写中 4=已提交 */
    uint32_t offset;       /* 下载断点偏移 */
    uint8_t  chunk_sha[32];/* 上一块哈希，续传前校验 */
    uint8_t  retry_cnt;    /* 重试计数，超限触发回滚 */
    uint32_t crc32;        /* 结构自身校验 */
} ota_state_t;

/* 原子写：先写 .tmp → fsync → rename，避免掉电写坏状态文件 */
snprintf(tmp, sizeof(tmp), "%s.tmp", STATE_FILE);
write_state(tmp, &st);
fsync(fd);
rename(tmp, STATE_FILE);
```
启动恢复逻辑：读状态 → 校验 magic/crc → 按 phase 分支（下载中→续传；校验中→重验；刷写中→查回滚标志）；状态损坏 → 保守策略（重新下载或回滚）。
**关联项目**：OTA 排查支持（断点续传故障）、GNSS 固件升级（升级状态机）

### UDS 刷写链路回顾（34/36/37）

**一句话要点**：刷写是 OTA 落地的最后一公里：进编程会话(10 02) → 安全访问(27) → 请求下载(34，声明地址/长度，隐含擦除) → 传输数据(36 分块) → 请求退出(37) → 例程校验(31) → 复位(11)；网络层经 CAN TP 或 DoIP，NRC 是定位刷写故障的钥匙。

**面试怎么问**：为什么刷写前要擦除 Flash？0x36 块序号到 0xFF 之后怎么办？NRC 0x33 / 0x31 / 0x78 分别代表什么？

**用例 / 示例**：
```text
刷写报文序列（CAN TP 承载）：
  10 02           → 进入编程会话          （响应 50 02）
  27 01           → 请求 seed             （响应 67 01 + seed）
  27 02 <key>     → 回发 key 解锁          （响应 67 02）
  34 00 44 <地址><长度> → 请求下载        （响应 74 + 块大小）
  36 01 <data...> → 传输块 1              （响应 76 01）
  36 02 <data...> → 传输块 2 …（0xFF 后回 0x00）
  37              → 请求退出传输           （响应 77）
  31 01 02 01 ... → 例程控制检查内存       （响应 71 …）
  11 01           → 复位 ECU               （响应 51 01）

常见 NRC：0x33 安全访问未通过 / 0x31 地址或长度越界 /
          0x78 响应挂起（继续等）/ 0x10 一般拒绝
```
详细帧格式与 CAN TP 多帧重组见「05-auto 车载协议与 OTA」。
**关联项目**：GNSS 固件升级（实际 UDS 刷写实现）、OTA 排查支持

### Bootloader 与 App 分区设计

**一句话要点**：bootloader 常驻只读/受保护分区（自身不可被普通 OTA 覆盖），负责上电自检、验签、选槽位、跳转 app；app 分区才是 OTA 的写入目标。升级 bootloader 必须走特殊流程（双 bootloader/独立升级通道），防止引导程序被刷坏导致整机变砖。

**面试怎么问**：bootloader 能被 OTA 升级吗？怎么保护？完整的启动流程是什么样的？

**用例 / 示例**：
```text
典型启动链（Secure Boot）：
  上电 → ROM(固化) 校验 Bootloader 签名 → Bootloader 校验 App 签名
      → 启动 App → 业务加载 → OTA 客户端就绪

Bootloader 职责：
  1. 硬件初始化（时钟/内存/存储）
  2. 启动校验：验签 App、校验槽位标志、回滚判定
  3. 升级引导：接收 UDS 刷写请求，提供 34/36/37 服务
  4. 跳转 App（或进入 recovery / 下载模式）

保护手段：
  - Bootloader 分区只读（eMMC 硬件写保护 / 权限控制）
  - 升级 bootloader 走独立流程：备用区双写保护 + 掉电保底
  - 核心原则：bootloader 坏了 = 变砖，一切 OTA 设计都要保证它永远能启动
```
**关联项目**：GNSS 固件升级（bootloader + app 双区）、OTA 排查支持

### 升级失败排查方法论（现场实战）

**一句话要点**：排查 = 按阶段定位 + 数据说话：先看升级状态码/阶段日志定位「卡在哪一环」（任务获取/下载/校验/刷写/提交），再抓对应日志与 UDS 报文确认根因；远程排查靠设备上报的状态机快照和分段日志。

**面试怎么问**：客户反馈 OTA 升级失败，你远程怎么排查？升级后反复重启怎么办？

**用例 / 示例**：
```text
排查决策表：
  现象                 | 优先怀疑                      | 排查手段
  没收到任务           | 车型/VIN 不在任务范围、网络不通 | 查任务下发记录、设备在线状态
  下载到 X% 失败       | 断网、空间不足、断点状态损坏    | 看下载日志、剩余空间、续传点
  下载完校验失败       | 包不完整、哈希不符、签名过期    | 重下、比对包哈希、验签日志
  刷写失败 NRC 0x33    | 安全访问未通过（seed/key）     | 抓 27 报文，查 seed 来源
  刷写失败 NRC 0x31    | 地址/长度越界、分区表不符      | 比对刷写地址与分区表
  刷写失败 NRC 0x78    | ECU 忙、超时                  | 看 P2/P2* 定时与重试策略
  刷完反复重启         | 槽位校验失败触发回滚           | 看启动日志、槽位标志、回滚计数
  差分包应用失败       | 基线版本不匹配                | 核对设备当前版本与补丁基线
  升级成功但功能异常   | 版本不兼容、配置/数据未迁移    | 对比版本差异、查配置迁移脚本

三板斧：① 状态码 + 阶段日志定环节 ② 抓报文/日志找根因 ③ 对照回滚策略恢复
```
**关联项目**：OTA 排查支持（核心方法论）、市场问题分析（批量故障定位）

### 常见故障案例库（复习用）

**一句话要点**：把真实故障浓缩成「现象 → 根因 → 处理」三元组，考前扫一遍，面试讲案例直接套 STAR 模板。

**面试怎么问**：讲一个你处理过的升级相关故障（STAR：情境-任务-行动-结果）。

**用例 / 示例**：
```text
案例 1：批量设备升级后反复重启
  根因：槽位切换后新分区校验失败（签名/哈希不符），反复触发回滚
  处理：抓启动日志确认槽位标志 → 定位为包体损坏 → 重新下发修复包并灰度

案例 2：某车型差分包应用失败率突增
  根因：线上基线版本统计错误，补丁按错误旧版本生成，设备基线不符
  处理：核对设备实际版本分布 → 服务端按实际版本生成/匹配 → 失败自动降级全量

案例 3：升级下载到 99% 一直失败
  根因：断点续传状态文件损坏（掉电），每次从损坏偏移续传
  处理：状态文件加 magic + crc 校验，损坏则重置断点重新下载（见断点续传卡片）

案例 4：刷写时报 0x33 安全访问拒绝
  根因：27 服务 key 算法与 seed 序号不同步 / 尝试次数锁定
  处理：抓 27 报文确认 seed 来源 → 同步算法与计数 → 规避连续失败锁定

案例 5：升级成功但部分功能不可用
  根因：版本升级后配置/证书未迁移（SOTA 配置包缺失）
  处理：升级清单增加配置迁移校验，升级后自检配置版本
```
**关联项目**：市场问题分析（eMMC-eSIM 专项同款排查思路）、OTA 排查支持

### OTA 术语速查表

**一句话要点**：面试/读日志必备的英文缩写速查：全称 + 一句话解释。不直接考缩写，但读英文文档和现场日志离不开。

**面试怎么问**：给一段 OTA 故障日志，要能一眼认出关键字段（phase / retry / slot / NRC / hash）。

**用例 / 示例**：
```text
术语速查：
  FOTA / SOTA    固件升级 / 软件升级
  OTA            Over-The-Air 空中升级
  A/B slot       双分区槽位方案（无缝升级 + 回滚）
  Seamless       无缝升级（升级不影响当前运行）
  Anti-rollback  防回滚（版本计数器只增不减）
  RPMB           Replay Protected Memory Block（安全存储，存回滚计数）
  Secure Boot    安全启动（逐级验签启动链）
  HSM            硬件安全模块（密钥存储 / 加解密）
  SHA-256        哈希校验（完整性）
  RSA / ECC      非对称签名算法
  AES            对称加密（包体加密）
  bsdiff         二进制差分算法（字节级）
  Delta / Patch  差分补丁
  Baseline       基线版本（差分包依赖的源版本）
  Gray release   灰度发布（分批放量）
  Rollback       回滚（失败恢复旧版本）
  Recovery       恢复模式（兜底刷机 / 恢复出厂）
  UDS 34/36/37   请求下载 / 传输数据 / 请求退出（刷写核心服务）
  DoIP           Diagnostic over IP（以太网诊断）
  CAN TP         ISO 15765-2（多帧传输，刷写底层）
```
