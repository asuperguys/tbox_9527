## 二、核心架构:参数注册表(m_paraCtlApiMap)— 面试核心!

### 设计思想

整个参数管理基于**"一张注册表"**模式:

```cpp
// 每个参数ID 对应一个描述结构
typedef struct ParaProcInfo_st {
    char table_name[32];      // 数据库表名
    char para_key[32];        // 数据库字段名(PARA_NAME)
    char para_type[32];       // 参数类型分组(如"BasicPara"/"DmsConf")
    char def_value[128];      // 默认值
    CONV_FUNCTION read_conv;  // 读取后转换函数
    CONV_FUNCTION write_conv; // 写入前转换函数
    LOAD_FUNCTION load_func;  // 加载函数(读取时执行)
    MORE_LOAD_FUNCTION more_load_func; // 多参数加载函数
    ProtocolParaType_e value_type;     // 参数值类型(字节/字/双字/字符串...)
    int max_len;              // 最大长度
    CONV_FUNCTION read_func;  // 读取函数
    CONV_FUNCTION write_func; // 写入函数
    ACTION_FUNCTION upd_action; // 更新后通知回调
} ParaProcInfo;
```

### 注册示例(RegSafetyParaFunc,safety_para_manager.cpp:52)

```cpp
// 心跳间隔:E_TERM_HB_INTVL=0x001F → AiSafetyBasicPara表 heartbeat字段
RegFunc(E_TERM_HB_INTVL, "AiSafetyBasicPara", "heartbeat", "BasicPara", "30",
        NULL, NULL, BIND2(ParseHeartBeat), NULL,
        PROROCOL_PARA_TYPE_BYTE, 1, NULL, NULL, TableUpdNotifySafetyPara);

// DMS打电话配置:E_DMS_PHONECALL_CONF → AiSafetyAlarmEventConf表 phoneCall_conf字段
RegFunc(E_DMS_PHONECALL_CONF, "AiSafetyAlarmEventConf", "phoneCall_conf", "DmsConf", "1,30,600",
        NULL, NULL, NULL, BIND5(paraseDmsAlarmPara),
        PROROCOL_PARA_TYPE_CUSTOM, 128, NULL, NULL, TableUpdNotifySafetyPara);
```

### 为什么这样设计(面试必答)

1. **新增参数零侵入**:加一个新参数 = 在注册函数里加一行 `RegFunc(...)`,不需要改上层代码。**配置驱动开发**。
2. **协议命令字 ↔ 数据库 ↔ 内存 三层解耦**:
   - 平台下发参数ID(0x8504命令字里的参数ID) → `m_paraCtlApiMap[event]` 找到表名/字段名
   - 读数据库 → 内存结构体
   - 统一由注册信息驱动,不用为每个参数写一堆 if-else
3. **类型与转换可配**:值类型(byte/word/dword/string)、读写转换函数、加载函数都可注册,灵活应对协议格式差异。
4. **更新通知**:`upd_action`(如 TableUpdNotifySafetyPara)在参数变更后触发,驱动"参数变了→通知算法重载"的联动。

### 面试话术示例

> "参数管理我采用了一张注册表的设计:每个参数ID对应一条注册记录,记录它存在哪张表、哪个字段、什么类型、默认值、怎么解析、更新后通知谁。
> 这样平台下发参数时,我只需要按ID查表就能完成'协议字节→数据库→内存结构'的全链路,新增一个参数就是加一行注册。三张表几百个参数都是这样管理的。"

## 三、数据库设计(面试必答)

### 库文件与表

```
/mnt/flash/SQLite/tm8765_para.db
├── AiSafetyBasicPara      # 设备基本参数
├── AiSafetyAlgPara        # 算法参数(含标定)
└── AiSafetyAlarmEventConf # 报警事件参数
```

### 统一表结构

```sql
CREATE TABLE ... (
    PARA_NAME     TEXT PRIMARY KEY,  -- 参数名(注册表的para_key)
    PARA_VALUE    TEXT,              -- 参数值(字符串存储)
    PARA_TYPE     TEXT,              -- 类型分组
    UPDATE_TIME   ...
);
```

> **关键设计:所有参数以字符串形式存储,按名字索引。** 不同分组(基本/算法/报警)分表,每表结构一致。这样表结构固定,新增参数只是新行,不需要迁移表结构。

## 四、参数解析函数(面试重点)

### 报警参数解析(paraseDmsAlarmPara 等)

```cpp
// conf 格式:"开关,灵敏度,间隔"
// 例:"1,30,600" → alarmEvent_switch=1, sensitive=30, interval=600
// action 格式:"触发速度,其他阈值,阈值1,阈值2,1级动作,2级动作,3级动作"
// 例:"10,0xff,30,60,0xff,0xff,0xff" → trigger_speed=10, trigger_other=0xff, level_1=30, level_2=60, 各级动作=0xff
```

解析后存入:
```cpp
struct AlarmEventPara_st {
    AlarmEventConf_t  alarmEventConf;   // 开关/灵敏度/间隔
    AlarmEventAction_t alarmEventAction; // 触发速度/阈值/分级动作
};
```

### 内存参数结构(SafetyAlarmEventPara_t)

```cpp
struct SafetyAlarmEventPara_st {
    // 各子事件参数集合(哈希表,key为事件类型)
    std::unordered_map<DMS_ALARM_TYPE_e, AlarmEventPara_t>  dmsAlarmEventParaMap;
    std::unordered_map<ADAS_ALARM_TYPE_e, AlarmEventPara_t> adasAlarmEventParaMap;
    std::unordered_map<int, unordered_map<int, AlarmEventPara_t>> bsdAlarmEventParaMap; // bsd1~4
    std::unordered_map<HMS_ALARM_TYPE_e, AlarmEventPara_t>  hmsAlarmEventParaMap;
    std::unordered_map<int, AlarmEventPara_t> threeUrgentAlarmEventParaMap; // 三急
    // ... 版本号/视频时长/超速/打哈欠计数等协议字段
};
```

> 面试点:用 `unordered_map` 以事件类型为key存参数,上层按 `Extern_SafetyConf_GetDmsConf(DMS_ALARM_TYPE_CALL)` 直接取某个子事件的配置,取不到返回默认值。

### 参数变更检测(ConfParaChangeInfo_st)

```cpp
struct ConfParaChangeInfo_st {
    int dmsConfParaChangeTimes = 0;   // 各模块参数变更计数
    int adasConfParaChangeTimes = 0;
    ...
    void IncrementDmsConfParaChangeTimes();  // 参数变化时++
```

> 用途:UI更新通知后,重新读库,比较"变更计数是否>0"判断参数是否真的变了,变了才触发算法重初始化。**避免无效重载**。

## 六、安卓App参数交互(JSON)— 你的产出亮点!

### JSON 结构(与 app_protocol.json 草案对应)

```json
{
  "adas": {
    "chn": 0,
    "CalibInfo": [ { "horizon": {"value":-1,"desc":"地平线","unit":"pixel","limit":">=0","type":"int"} } ],
    "parameters": [ { "fx": {"value":-1.0,"desc":"焦距",...} } ]
```

### 三大能力(面试重点)

1. **下发解析**(App → 终端):`parseAlgJsonPara` — 解析JSON,校验值范围,映射到参数ID,写库
   - 模块枚举:fr/dms/adas/hms/bsd1~bsd4/safetyDevBasicCfg
   - 组件:CalibInfo(标定)/ parameters(页面设置)
   - 校验:RangeTypeValue_t(>= / <= / (a,b) / [a,b] 等),`CheckValueIsInLimit`
   - 错误码:AlgJsonErrorCode_e(1001 ADAS标定非法、3002 DMS页面参数非法...)
2. **上传组包**(终端 → App):`sendAllAlgJsonPara` — 把当前所有参数组JSON返回
3. **多语言**:中/英/泰三语描述(multi_language_def.h),按语言flag切换

### 面试话术

> "安卓App的参数交互我做的:App通过调试通道发JSON下来设置算法参数——比如ADAS标定的地平线、焦距,或者DMS各事件的开关灵敏度。
> 我实现了JSON解析、参数范围校验(比如灵敏度的合法范围)、按模块映射到数据库参数ID、写库并通知算法侧。
> 返回的时候把当前所有配置组JSON返回给App,支持中文英文泰文三语描述,因为项目有泰国版本。"

## 八、你在这个模块的"面试故事"建议

### 叙事建议:
> "参数管理我负责的。整个系统有几百个参数,来自三个途径:平台下发、安卓App设置、本地默认值。
> 我设计了一张参数注册表,每个参数注册一次,记录它存在哪张表、什么字段、类型、默认值、解析函数、更新通知。平台下发时按ID查表就能完成全链路存取,App设置走JSON解析,都汇聚到这张表。
> 难点在于参数变更后的联动——比如App改了DMS灵敏度,我需要判断参数是否真的变了,变了才通知算法侧重新加载,避免无效的重初始化导致算法重启。"
