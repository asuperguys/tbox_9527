## 一、CAN 总线基础(必考,宇通场景直接相关)

### 1.1 是什么
> CAN(Controller Area Network,控制器局域网)是**车载分布式控制系统**的标准现场总线,
> 由博世开发,ISO 11898 标准化。特点:**多主从、差分信号、双线、抗干扰**。

### 1.2 关键特性(面试必讲)
| 特性 | 说明 | 面试怎么讲 |
|---|---|---|
| 多主访问 | 总线上任意节点可发帧,无主从 | "任何节点都能主动发,仲裁解决冲突" |
| 非破坏性仲裁 | 按 ID 优先级,ID 小的优先 | "同时发送时,ID 小的(优先级高)自动赢得总线" |
| 差分信号 | CAN_H / CAN_L 两根线 | "抗共模干扰,适合车上电噪声环境" |
| 错误处理 | CRC、位填充、错误帧 | "协议层自带检错,节点错误率超限自动离线" |
| 报文类型 | 数据帧/远程帧/错误帧/过载帧 | 重点讲数据帧:SOF/仲裁场/控制场/数据场/CRC/ACK/EOF |

### 1.3 标准帧 vs 扩展帧
| 帧类型 | ID 长度 | 标识 |
|---|---|---|
| 标准帧 | 11 位 ID | 常见于动力/底盘 |
| 扩展帧 | 29 位 ID | 常见于诊断/多 ECU 系统 |

### 1.4 波特率
> 常见 125kbps / 250kbps / 500kbps / 1Mbps。整车常用 500k(动力 CAN)。
> 位时间 = 同步段+传播段+相位缓冲段1+2,可采样点调整。

### 1.5 面试话术(结合宇通)
> "整车 CAN 大概 1700 帧/秒,这相当于每 0.6ms 一帧。CAN 总线本身带宽有限(比如 500kbps),所以报文都是短帧(最多 8 字节数据),大量小报文高频轮发。处理的关键不是'每帧做什么',而是**按信号组织、批量消费、及时失效**——这也是我做信号级框架的原因。"

## 二、车载网络协议栈(面试"你了解车联网吗"时讲)

### 2.1 分层视角
```
应用层     诊断/服务(如 UDS/DoIP)
传输层     ISO-TP(传输大数据,分包重组)
网络层     ...
数据链路层  CAN / CAN-FD / LIN / FlexRay / Ethernet
物理层      差分线/光纤
```

### 2.2 常见总线对比(面试加分)
| 总线 | 速率 | 用途 |
|---|---|---|
| CAN | 最高 1Mbps | 动力/底盘/车身控制 |
| CAN-FD | 数据段最高 8Mbps | 大数据量场景(升级/诊断) |
| LIN | 20kbps | 低成本低速(车窗/座椅) |
| FlexRay | 10Mbps | 线控/安全关键(较少) |
| 车载以太网 | 100M/1G | 娱乐/ADAS 大数据 |

### 2.3 ISO-TP(传输层)
> CAN 单帧最多 8 字节,大消息(如诊断数据)要**分包**:
> 单帧(SF)≤7字节 → 首帧(FF)+连续帧(CF)流控(FC)。
> 你的项目报文走域通信转发而非直接 CAN,所以没用到 ISO-TP,但了解概念即可。

## 三、AUTOSAR(面试"你听过吗"时讲)

### 3.1 是什么
> AUTOSAR(Automotive Open System Architecture)是**汽车电子软件标准化架构**,
> 由 OEM+供应商共同定义,目标是软硬件解耦、应用可移植。

### 3.2 分层(经典版)
```
应用层(ASW): 业务逻辑,与硬件无关
├── RTE(运行时环境): 应用与BSW的通信中间层
└── BSW(基础软件):
    ├── 服务层(通信管理/诊断/状态管理)
    ├── ECU抽象层(驱动抽象)
    └── MCAL(微控制器抽象,直接操作硬件)
```

### 3.3 与你的项目对应(面试点睛!)
> "我的 CAN 信号级框架思路和 AUTOSAR COM(通信模块)很像:
> COM 就是把 PDU 拆成**信号**,信号有**超时监控**、有**更新机制**;
> 我做的是在应用层用轻量方式实现了同样的思想——信号注册表+信号槽+超时,零依赖可移植。"

> 这句点睛非常加分:说明你**理解行业标准,并能用自己的实践印证它**。

## 四、SocketCAN(面试"你用过 Linux CAN 吗"时讲)

### 4.1 是什么
> SocketCAN 是 Linux 内核的 CAN 协议栈实现,把 CAN 接口抽象成 **socket**:
> `socket(PF_CAN, SOCK_RAW, CAN_RAW)` → `bind` 到接口(can0)→ 读写信封。

### 4.2 关键概念
- **can_id**:报文 ID(含 EFF/RTR 标志位)
- **can_dlc**:数据长度(0-8)
- **CAN_RAW_FILTER**:按 ID 过滤(内核级,省用户态处理)
- **CANFD**:canfd_frame 结构(64 字节)
- **candump / cansend / cangen**:调试工具

### 4.3 面试话术
> "如果设备直接连 CAN 总线(比如宇通整车),我会用 SocketCAN:内核按 ID 过滤、原始帧收发、canutils 调试。但天迈这个项目数据是调度经域通信转发的私有封装报文,不是标准 CAN 接口,所以我在应用层自建了信号管理。两种方式我都有思路。"

## 七、可能被问的延伸问题(自测)

**Q1: CAN 和 CAN-FD 区别?**
> CAN-FD 数据段最高 8Mbps(普通 CAN 1Mbps),单帧最多 64 字节(普通 8 字节),用于大数据场景(诊断/升级)。仲裁机制相同,向后兼容。

**Q2: 为什么整车用 CAN 而不是以太网?**
> 历史原因+成本+确定性:CAN 便宜、抗干扰、仲裁机制保证实时性(确定性时延);以太网带宽大但成本和复杂度高。现在高端车型引入车载以太网用于 ADAS/娱乐大数据,与 CAN 并存。

**Q3: CAN 报文丢失怎么办?**
> 协议层检错重发(CAN 本身有重发机制);应用层靠**信号超时**感知失效 + **周期报文**设计(丢失会被下个周期覆盖)。所以"状态型信号超时置无效"是 CAN 应用的标准做法——这正是我做的。

**Q4: 1700帧/s 是什么概念?怎么验证不丢帧?**
> 1700帧/s ≈ 每 0.6ms 一帧,500kbps 总线利用率约 27%(按 8 字节帧算)。验证:接收端统计帧计数/CRC 错误率,用 canfd 或日志打点;处理端看 CPU 占用和队列积压。

**Q5: AUTOSAR COM 和你做的信号框架区别?**
> COM 是完整规范(含 PDU 路由、I-PDU 信号组、超时监控、周期发送);我做的是应用层轻量实现,只取"信号+超时+变化检测"核心思想,零依赖可移植。方向一致,复杂度按需裁剪——这也是我在 [14 文档](#/tm-14)复盘里承认"对天迈偏重"的原因。
